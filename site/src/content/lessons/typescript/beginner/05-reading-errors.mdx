You will read far more compiler errors than you write programs without them, especially at first. The messages look long and technical, but they follow a pattern, and the pattern usually points at the fix. This lesson teaches the pattern. The general habits of finding and fixing bugs are in the fundamentals lesson on [debugging](../../../fundamentals/beginner/debugging/), and the [JavaScript debugging lesson](../../../javascript/beginner/debugging-js/) covers run-time errors, which are a different kind.

## Anatomy of an error

An error has three parts: where, which, and what. This file contains four mistakes:

```ts title="error_tour.ts"
const total: number = "10";

function square(n: number) {
  return n * n;
}
console.log(square("4"));

const user = { name: "Ada" };
console.log(user.age);

function twice(x) {
  return x * 2;
}
console.log(twice(3));
```

`tsc --pretty false` prints one line per error, which is easy to compare and to search for. In a terminal you get the multi-line coloured form from the earlier lessons.

```bash frame="terminal"
npx tsc --noEmit --ignoreConfig --pretty false error_tour.ts
```

```text
error_tour.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
error_tour.ts(6,20): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
error_tour.ts(9,18): error TS2339: Property 'age' does not exist on type '{ name: string; }'.
error_tour.ts(11,16): error TS7006: Parameter 'x' implicitly has an 'any' type.
```

Take the first line apart:

- `error_tour.ts(1,7)`: file, line 1, column 7. The column marks the start of the thing that is wrong, here the name `total`.
- `TS2322`: the error code. It is stable, so you can search for it and compare notes with other people.
- The sentence: **what the compiler saw**. Read "X is not assignable to Y" as "a value of type X cannot go where Y is required".

Notice that the file also contains a call `twice(3)` that works at run time. The compiler reports on every line, and keeps going after the first error. Fix the top error first anyway, because one mistake often causes several messages.

## The four errors you will meet first

| Code | Message starts | Usual cause | Usual fix |
|---|---|---|---|
| `TS2322` | Type 'A' is not assignable to type 'B' | A value of the wrong type was stored or returned | Fix the value, or fix the annotation if the annotation is wrong |
| `TS2345` | Argument of type 'A' is not assignable to parameter of type 'B' | A function was called with the wrong kind of argument | Convert or fix the argument |
| `TS2339` | Property 'p' does not exist on type 'T' | A typo, or the object never had that property | Correct the name, or add the property to the type |
| `TS7006` | Parameter 'x' implicitly has an 'any' type | A parameter has no annotation and no context to infer it from | Annotate the parameter |

Sometimes the compiler adds a suggestion, such as `Did you mean 'length'?` after a misspelled property. TypeScript checks the word against the properties that exist, so a suggestion like that is almost always right.

Decide which side is wrong before you change anything. In `TS2322`, the value might be wrong, or the annotation might be. The compiler cannot know which you meant.

## Let the editor help

Editors such as Visual Studio Code use the same compiler and show errors as you type, as a red squiggle under the code. Three features save the most time:

- **Hover** over a name to see its type. This is how you find out what the compiler believes, which is often different from what you assumed.
- **Go to definition** (F12 in Visual Studio Code) jumps to where a function, variable or type is declared.
- **Quick fix** (the light bulb, or Ctrl+. or Cmd+.) offers repairs, such as adding a missing annotation or fixing a misspelled name.

If the editor and `tsc` ever disagree, check which TypeScript version each one uses.

## Silencing an error on purpose

Sometimes you want a line that is deliberately wrong, for example to test that a function rejects bad input. A comment placed directly above the line tells the compiler to expect an error there:

```ts title="expect_error.ts"
function square(n: number): number {
  return n * n;
}

// @ts-expect-error: the point of this call is the wrong type
console.log(square("4"));
```

```bash frame="terminal"
npx tsc --noEmit --ignoreConfig expect_error.ts
node expect_error.ts
```

```text
16
```

The compiler passes with no output. If the line later stops being an error, `@ts-expect-error` itself becomes an error, so the comment cannot go stale:

```ts title="expect_unused.ts"
function square(n: number): number {
  return n * n;
}

// @ts-expect-error: this call is fine, so the comment is wrong
console.log(square(4));
```

```bash frame="terminal"
npx tsc --noEmit --ignoreConfig --pretty false expect_unused.ts
```

```text
expect_unused.ts(5,1): error TS2578: Unused '@ts-expect-error' directive.
```

The older comment `// @ts-ignore` does the same silencing but never complains, even when it hides nothing. Prefer `@ts-expect-error`, and write a reason after the colon. Use neither to quiet a real problem you have not understood.

## Common pitfalls

- **Fixing the last error first.** Start at the top; later errors often disappear.
- **Silencing instead of fixing.** A `@ts-expect-error` on a real bug leaves the bug in the program.
- **Changing an annotation until the error goes away.** Decide whether the value or the annotation is the mistake.
- **Searching for the message text with your own names in it.** Search for the error code and the generic part of the sentence instead.

```ts
const planet: number = "Mars";
const moons: string = 2;

function describe(name: string, count: number): string {
```

<Solution>

```ts title="fix_three.ts"
const planet: string = "Mars";
const moons: number = 2;

function describe(name: string, count: number): string {
  return `${name} has ${count} moons`;
}

console.log(describe(planet, moons));
```

```text
Mars has 2 moons
```

The annotations on the two constants were swapped, which gave the two `TS2322` errors. Correcting them exposes two `TS2345` errors, because the call also passes its arguments in the wrong order. One fix can reveal the next problem, so run the compiler again after each round. Here the annotations were the mistake and the values were right.

<Exercise title="Test that a call is rejected">

Write `repeat(text: string, times: number): string` that returns `text.repeat(times)`. Add a call `repeat("ab", "3")` that you expect the compiler to reject, and mark it so that `tsc --noEmit` passes. Print the result. <Solution>

```ts title="expect_wrong_call.ts"
function repeat(text: string, times: number): string {
  return text.repeat(times);
}

// @ts-expect-error: times must be a number
console.log(repeat("ab", "3"));
```

```text
ababab
```

Remove the comment and `tsc` reports `TS2345`. That is how you know the comment is doing its job.

</Solution>

## Recap

- An error line has a location, a code such as `TS2322`, and a message. Start with the first error.
- `TS2322`, `TS2345`, `TS2339` and `TS7006` cover most beginner mistakes. Decide whether the value or the annotation is wrong.
- Hover, go to definition and quick fix make the editor a second way to read the compiler's mind.
- Prefer `// @ts-expect-error` with a reason over `// @ts-ignore`. It reports itself when it is no longer needed.
