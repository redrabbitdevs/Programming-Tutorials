This lesson has no new topics. It takes a real program through a security review: decide what could go wrong, look for it, fix it, prove each fix with a test, and record what you chose not to fix.

The program is **lnk**, the link shortener from the [advanced project](../../advanced/project-fullstack/): a `node:http` JSON API and a browser client that share one validation module, with no npm dependencies. The reviewed copy is `e3/sr_lnk/`; the original stays in `a4/lnk/`.

## Step 1: the threat model

A threat model answers four questions. Write it before reading the code, so the code does not decide what you look for.

| Question | For lnk |
|---|---|
| What are we protecting? | The stored links (their integrity), the server (its availability), and visitors who follow short links |
| Who can reach it? | Anyone on the internet, with no account |
| Where does input enter? | `POST /api/links` (a JSON body), `GET /<code>`, `GET /api/links/<code>`, and the three static files |
| What is the worst outcome? | A short link that runs script or misleads a visitor; one request that stops the server for everyone |

Each row becomes a check: input that becomes code or a header ([security bugs](../js-security-bugs/)), browser defences, errors and slow clients, and what the process can reach ([permissions](../node-permission-model/)).

## Step 2: probe the running app

`sr_probe.mjs` starts the **original** app and sends it an attacker's requests:

```javascript title="sr_probe.mjs"
// Probes the advanced project's link shortener, unchanged, for the
// findings in the security review. Run from this folder: node sr_probe.mjs
import { createApp } from "../a4/lnk/server/app.mjs";
import { createStore } from "../a4/lnk/server/store.mjs";

const lines = [];
const server = createApp(createStore(), { write: (l) => lines.push(l) });
await new Promise((resolve) => server.listen(0, "127.0.0.1", resolve));
const base = `http://127.0.0.1:${server.address().port}`;

const shorten = async (url) => {
  const response = await fetch(`${base}/api/links`,
    { method: "POST", body: JSON.stringify({ url }) });
  return [response.status, await response.json()];
};
```

It checks the headers, a URL with a line break, a URL with a user name, and a prototype member as a code:

```javascript title="sr_probe.mjs (continued)"
// 1. Which security headers does the page carry?
const page = await fetch(base);
for (const name of ["content-security-policy", "x-content-type-options"]) {
  console.log(`${name}:`, page.headers.get(name));
}

// 2. A link with a line break in it is accepted...
const withBreak = "https://example.com/a\r\nSet-Cookie: x=1";
const [status, link] = await shorten(withBreak);
console.log("line break accepted:", status);
// ...and every visit to it then fails.
const visit = await fetch(`${base}/${link.code}`, { redirect: "manual" });
console.log("visit:", visit.status);
console.log(lines.at(-2).split("\n")[0]);
```

The last part also prints the server's timeouts:

```javascript title="sr_probe.mjs (continued)"
// 3. A link that hides its real host behind a user name.
const [hidden] = await shorten("https://bank.example@phish.example/login");
console.log("user name in URL accepted:", hidden);

// 4. Codes that name Object.prototype members.
const proto = await fetch(`${base}/api/links/constructor`);
console.log("constructor code:", proto.status);
console.log("server timeouts:", server.requestTimeout, server.headersTimeout);
server.close();
```

```text
content-security-policy: null
x-content-type-options: null
line break accepted: 201
visit: 500
req 3: TypeError [ERR_INVALID_CHAR]: Invalid character in header content ["Location"]
user name in URL accepted: 201
constructor code: 404
server timeouts: 300000 60000
```

Some things are right already: the store is a `Map`, so `constructor` is an unknown code; static files come from a fixed table; errors are answered with a plain `internal error`; and `javascript:` links were refused.

The findings, worst first:

1. **No security headers.** A future XSS bug would run unhindered, and any site may frame the page.
2. **A crash on a failed file read**, found in step 4.
3. **Line breaks accepted.** `URL.canParse` ignores them, so the raw text is stored. Node refuses it in a `Location` header, so every visit is a 500.
4. **User names accepted.** The link goes to `phish.example`; `bank.example@` only fools a reader.
5. **A five-minute request timeout,** the `node:http` default.

## Step 4: headers, and an error path that crashed

Every response now carries a Content Security Policy and two smaller headers:

```diff
+// Sent with every response. The page has no inline code, so the policy
+// can forbid everything but this origin's own scripts.
+const SECURITY_HEADERS = {
+  "Content-Security-Policy": "default-src 'self'; object-src 'none'; " +
+    "base-uri 'none'; frame-ancestors 'none'; form-action 'self'; " +
+    "require-trusted-types-for 'script'",
+  "X-Content-Type-Options": "nosniff",
+  "Referrer-Policy": "no-referrer",
+};
```

`default-src 'self'` allows code and requests only from the app's own origin, so an injected `<script>` or `onclick` does not run. `frame-ancestors 'none'` stops framing, and `require-trusted-types-for 'script'` makes HTML sinks refuse strings, which costs nothing because `client.js` only uses `textContent`. `handle` sets the headers before routing, so error responses carry them too. The policy can be this strict because all code is in files; the second exercise finds inline code in an older page.

Running the original app with no read grant for `public/` found the crash. <Since v="25" /> `--allow-net` needs Node 25; on 22 and 24, leave it out, since the network is open there.

```text frame="terminal"

    at serveFile (a4/lnk/server/app.mjs:68:22)
    …

node:_http_server:422
    throw new ERR_HTTP_HEADERS_SENT('write');
          ^

Error [ERR_HTTP_HEADERS_SENT]: Cannot write headers after they are sent …
    at ServerResponse.writeHead (node:_http_server:422:11)
    at sendJson (a4/lnk/server/app.mjs:16:12)
```

`serveFile` wrote the `200` status line, then awaited the read. When it failed, the handler's `500` hit a response that had already started, and that error killed the process. A missing file would do the same in production. The fix reads before writing anything:

```diff
 async function serveFile(response, [path, type]) {
+  // Read first: if reading fails, no headers have been sent yet, and the
+  // error handler can still answer 500.
+  const body = await readFile(join(root, path));
   response.writeHead(200, { "Content-Type": type });
-  response.end(await readFile(join(root, path)));
+  response.end(body);
 }
```

The timeout needs one option: `createServer({ requestTimeout: 10_000 }, ...)`.

## Step 6: a test for every fix

`test/security.test.mjs` runs next to the original tests. `execFileSync` and `join` are for the crash test:

```javascript title="sr_lnk/test/security.test.mjs"
import { after, before, describe, it } from "node:test";
import assert from "node:assert/strict";
import { execFileSync } from "node:child_process";
import { join } from "node:path";
import { createApp } from "../server/app.mjs";
import { createStore } from "../server/store.mjs";
```

It starts the app as the other tests do:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
describe("security review fixes", () => {
  let server;
  let base;
  before(async () => {
    server = createApp(createStore(), { write: () => {} });
    await new Promise((resolve) => server.listen(0, "127.0.0.1", resolve));
    base = `http://127.0.0.1:${server.address().port}`;
  });
  after(() => server.close());

  const shorten = (url) => fetch(`${base}/api/links`, {
    method: "POST",
    body: JSON.stringify({ url }),
  });
```

The header test includes an API error and a 404, where headers are most often forgotten:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  it("sends a strict CSP and nosniff on every response", async () => {
    for (const path of ["/", "/api/links/nope", "/nope"]) {
      const { headers } = await fetch(base + path);
      assert.match(headers.get("content-security-policy"),
        /default-src 'self'.*require-trusted-types-for 'script'/);
      assert.equal(headers.get("x-content-type-options"), "nosniff");
    }
  });
```

Each validation fix gets a case:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  it("rejects links with line breaks or credentials", async () => {
    const cases = {
      "https://example.com/a\r\nSet-Cookie: x=1":
        "no spaces or control characters",
      "https://bank.example@phish.example/login":
        "no user names or passwords in links",
    };
    for (const [url, error] of Object.entries(cases)) {
      const response = await shorten(url);
      assert.equal(response.status, 400);
      assert.deepEqual(await response.json(), { error });
    }
  });
```

This one pins down behaviour that was already right:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  it("treats prototype names as unknown codes", async () => {
    for (const code of ["constructor", "__proto__", "toString"]) {
      assert.equal((await fetch(`${base}/api/links/${code}`)).status, 404);
      const visit = await fetch(`${base}/${code}`, { redirect: "manual" });
      assert.equal(visit.status, 404);
    }
  });
```

The crash needs a process that cannot read `public/`, so the test runs this module in a child process:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  // A child process starts the app, requests the page and then an unknown
  // code, and prints each status and error. It runs from the app folder.
  const child = `
    import { createApp } from "./server/app.mjs";
    import { createStore } from "./server/store.mjs";
    const server = createApp(createStore(), { write: () => {} });
    await new Promise((done) => server.listen(0, "127.0.0.1", done));
    const base = "http://127.0.0.1:" + server.address().port;
    for (const path of ["/", "/api/links/nope"]) {
      const response = await fetch(base + path);
      console.log(response.status, (await response.json()).error);
    }
    server.close();`;
```

It expects a 500 and then a normal 404. Against `a4/lnk` the child dies, `execFileSync` throws, and the test fails:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  it("answers 500 when a file read fails, and keeps serving", () => {
    // No read grant for public/, so reading index.html fails. --allow-net
    // exists from Node 25; on 22 and 24 the network is open anyway.
    const flags = ["--permission", "--allow-fs-read=server",
      "--allow-fs-read=shared", "--input-type=module", "-e", child];
    if (process.allowedNodeEnvironmentFlags.has("--allow-net")) {
      flags.unshift("--allow-net");
    }
    const output = execFileSync(process.execPath, flags,
      { cwd: join(import.meta.dirname, ".."), encoding: "utf8" });
    assert.equal(output, "500 internal error\n404 not found\n");
  });
```

The last test checks the timeout:

```javascript title="sr_lnk/test/security.test.mjs (continued)"
  it("limits how long a request may take", () => {
    assert.equal(server.requestTimeout, 10_000);
  });
});
```

## Step 7: write down what you accept

A review ends with the risks you keep, and why:

- **Open redirects by design.** A preview page or a phishing blocklist is a product decision.
- **No rate limit.** The [advanced project's third exercise](../../advanced/project-fullstack/) adds one.
- **No authentication, an in-memory store.** Changing either changes the threat model.
- **Dependencies.** The first `npm install` brings the [supply chain](../supply-chain/) review with it.

## Common pitfalls

- **Reviewing only the happy path.** The second-worst finding was in error handling.
- **Fixing one side only.** Validation in `shared/` keeps browser and server in agreement.
- **Not testing error pages for headers.** Test a 404.
- **A fix without a test.** Each fix here has one.
- **Treating the review as finished.** Repeat it when the threat model changes.

<Exercise title="Find the grants with audit mode">

<Since v="24.20" /> Write `sr_ex_audit.mjs`, which subscribes to the permission audit channels, then imports the reviewed app, starts it, requests its three files and stops. Print each `permission` and `resource` once, sorted, with paths relative to `sr_lnk` and an empty resource shown as `(any)`. Run it with `--permission-audit`. The expected output is five `FileSystemRead` lines (`public/client.js`, `public/index.html`, `server/app.mjs`, `server/store.mjs`, `shared/links.mjs`) and two `Net` lines, `(any)` and `127.0.0.1`. Node 24 records no `Net` lines, because its model does not restrict the network.

<Solution>

```javascript title="sr_ex_audit.mjs"
// Run with: node --permission-audit sr_ex_audit.mjs
// Lists every resource the hardened app touches while serving its pages.
import { channel } from "node:diagnostics_channel";
import { isAbsolute, relative } from "node:path";

const touched = new Set();
function record({ permission, resource }) {
  const where = isAbsolute(resource) ? relative("sr_lnk", resource)
    : resource || "(any)";
  touched.add(`${permission} ${where}`);
}
for (const scope of ["fs", "net", "child", "worker"]) {
  channel(`node:permission-model:${scope}`).subscribe(record);
}

// Import after subscribing, so the module loads are recorded too.
const { createApp } = await import("./sr_lnk/server/app.mjs");
const { createStore } = await import("./sr_lnk/server/store.mjs");
const server = createApp(createStore(), { write: () => {} });
await new Promise((resolve) => server.listen(0, "127.0.0.1", resolve));
const base = `http://127.0.0.1:${server.address().port}`;
for (const path of ["/", "/client.js", "/links.mjs"]) await fetch(base + path);
server.close();

for (const entry of [...touched].sort()) console.log(entry);
```

```text frame="terminal"

FileSystemRead public/index.html
FileSystemRead server/app.mjs
FileSystemRead server/store.mjs
FileSystemRead shared/links.mjs
Net (any)
Net 127.0.0.1
```

The `(any)` entry is `listen`, which has no host. These are exactly the grants in `start:locked`: three folders to read, and the network.

<Exercise title="Find what a strict CSP would block">

Before adding a policy without `'unsafe-inline'` to an older page, list what it would break. Write `inlineCode(html)`, which counts inline `<script>` elements (without `src`), event handler attributes such as `onclick=`, inline `<style>` elements, `style=` attributes and `javascript:` links. Run it on a sample legacy page and on `sr_lnk/public/index.html`. The expected output for the legacy page is one inline script, two event handlers, one style attribute and one `javascript:` URL; for `sr_lnk` it is an empty list.

<Solution>

```javascript title="sr_ex_inline.mjs"
import { readFileSync } from "node:fs";

// Things a policy of script-src 'self' without 'unsafe-inline' blocks.
const RULES = [
  [/<script(?![^>]*\bsrc=)[^>]*>/gi, "inline <script>"],
  [/\son[a-z]+\s*=/gi, "event handler attribute"],
  [/<style[\s>]/gi, "inline <style> (needs style-src)"],
  [/\sstyle\s*=/gi, "style attribute (needs style-src)"],
  [/href\s*=\s*["']?javascript:/gi, "javascript: URL"],
];

function inlineCode(html) {
  const found = [];
  for (const [pattern, label] of RULES) {
    const count = html.match(pattern)?.length ?? 0;
    if (count > 0) found.push(`${count} x ${label}`);
  }
  return found;
}

const legacy = `<button onclick="save()">Save</button>
<script>window.config = { debug: true };</script>
<p style="color: red">Error</p>
<a href="javascript:void(0)" onmouseover="tip()">?</a>
<script type="module" src="/app.js"></script>`;

console.log("legacy page:", inlineCode(legacy));
const page = readFileSync("sr_lnk/public/index.html", "utf8");
console.log("sr_lnk page:", inlineCode(page));
```

```text
legacy page: [
  '1 x inline <script>',
  '2 x event handler attribute',
  '1 x style attribute (needs style-src)',
  '1 x javascript: URL'
]
sr_lnk page: []
```

Regular expressions are good enough for a first inventory of your own pages, not for parsing hostile HTML. The browser's own report is the final word: send the policy as `Content-Security-Policy-Report-Only` first and watch the console.

</Solution>

</Exercise>

<Exercise title="Grade the response headers">

Write `grade(appDir)`, which starts the app in `appDir`, requests `/`, `/client.js` and `/api/links/nope`, and returns the names of required headers that are missing or wrong on any of them: a CSP with `default-src 'self'` and `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and a `Referrer-Policy` of `no-referrer` or `same-origin`. Grade both apps. The expected output is all three names for `../a4/lnk` and an empty list for `sr_lnk`.

<Solution>

```javascript title="sr_ex_headers.mjs"
// Grade the security headers of the advanced project and the reviewed one.
const REQUIRED = {
  "content-security-policy": (v) => /default-src 'self'/.test(v) &&
    /frame-ancestors 'none'/.test(v),
  "x-content-type-options": (v) => v === "nosniff",
  "referrer-policy": (v) => v === "no-referrer" || v === "same-origin",
};

async function grade(appDir) {
  const { createApp } = await import(`./${appDir}/server/app.mjs`);
  const { createStore } = await import(`./${appDir}/server/store.mjs`);
  const server = createApp(createStore(), { write: () => {} });
  await new Promise((resolve) => server.listen(0, "127.0.0.1", resolve));
  const base = `http://127.0.0.1:${server.address().port}`;
  const missing = new Set();
  for (const path of ["/", "/client.js", "/api/links/nope"]) {
    const { headers } = await fetch(base + path);
    for (const [name, ok] of Object.entries(REQUIRED)) {
      if (!ok(headers.get(name) ?? "")) missing.add(name);
    }
  }
  server.close();
  return [...missing];
}

console.log("../a4/lnk missing:", await grade("../a4/lnk"));
console.log("sr_lnk missing:", await grade("sr_lnk"));
```

```text
../a4/lnk missing: [
  'content-security-policy',
  'x-content-type-options',
  'referrer-policy'
]
sr_lnk missing: []
```

Run a check like this in CI against the real server, so that a refactor of the routing cannot drop the headers from one kind of response.

</Solution>

## Self-check: the expert level

One question per lesson of the level.

1. Why does a hot function get faster, and what slows it again?
2. Why can adding properties in a different order slow reads?
3. When is a short-lived object not cheap?
4. Memory grows with every request. Is the collector at fault?
5. Does WebAssembly need warming up?
6. Why is a benchmark of an unused result impossibly fast?
7. High total time, no self time: where is the time?
8. Why does awaiting a resolved promise not yield to I/O?
9. What do the compile cache and a startup snapshot each save?
10. Why can iterator helpers allocate more than array methods?
11. How can merging parsed JSON change every object?
12. Does `--permission` stop a malicious package?
13. With `ignore-scripts=true`, how do you build one package?
14. Why compare an HMAC with `timingSafeEqual`, not `===`?
15. Why record accepted risks?

<details>
<summary>Answers</summary>

1. Feedback-driven tier-up; a new type deoptimizes it ([engine pipeline](../engine-pipeline/)).
2. Different hidden classes make the read polymorphic ([inline caches](../shapes-inline-caches/)).
3. When it survives, and is copied and promoted ([garbage collection](../garbage-collection/)).
4. No: something keeps it reachable ([memory leaks](../memory-leaks/)).
5. Yes: Liftoff first, TurboFan when hot ([WebAssembly](../webassembly-interop/)).
6. The JIT removed the unused work ([measuring](../measuring-performance/)).
7. In the functions it calls ([profiling](../profiling-node/)).
8. Microtasks all run before timers and I/O ([event loop](../event-loop-performance/)).
9. Compiling again; running initialisation again ([startup](../startup-snapshots-cache/)).
10. Each step creates a `{ value, done }` object ([data-oriented code](../data-oriented-js/)).
11. A `"__proto__"` key writes into `Object.prototype` ([security bugs](../js-security-bugs/#prototype-pollution)).
12. No: it contains mistakes, not malice ([permissions](../node-permission-model/)).
13. `npm rebuild <name> --ignore-scripts=false` ([supply chain](../supply-chain/)).
14. `===` leaks through timing how much matched ([cryptography](../crypto-and-secrets/)).
15. So the next review starts from them (step 7).

</details>
