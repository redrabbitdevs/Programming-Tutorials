[The first beginner lesson](../../beginner/what-is-javascript/) split JavaScript into a specification, engines and runtimes. Node runs on V8, the engine Google also uses in Chrome. This module opens V8 up: how it compiles and optimises code, how objects are laid out, how memory is reclaimed, and how to find leaks. Knowing this does not change how you write most code. It changes how you read a profile, and which explanations you believe.

Every engine claim here is checked against the [V8 source at tag 14.6.202](https://github.com/v8/v8/tree/14.6.202), the V8 inside Node 26.11.1, or shown with a real run. Engines change between versions, so every run that uses V8 flags is labelled with its version. Check yours:

```text frame="terminal"
$ node -p process.versions.v8
14.6.202.34-node.37
```

## Two flags for looking inside

V8 has hundreds of options of its own. `node --v8-options` lists them with their defaults, and Node passes any of them on. Two kinds appear in this module:

- **Tracing flags** such as `--trace-opt`, `--trace-deopt` and `--print-bytecode` print what the engine is doing.
- **`--allow-natives-syntax`** lets a script call V8's internal test functions, written with a `%` prefix, such as `%HaveSameMap(a, b)`. Without the flag, `%` there is a syntax error. The functions are listed in [`runtime.h`](https://github.com/v8/v8/blob/14.6.202/src/runtime/runtime.h) and exist for V8's own tests. They change without notice, so use them to learn and to investigate, never in code you ship.

## Parsing is lazy

When V8 loads a file it does not compile every function. With lazy compilation (the `--lazy` flag, on by default), most function bodies are only **pre-parsed**: the preparser checks the syntax "in order to understand the program sufficiently" and records what a later full parse needs ([`preparser.h`](https://github.com/v8/v8/blob/14.6.202/src/parsing/preparser.h)). The full parse and the compilation to bytecode happen the first time the function is called. Code that never runs costs little more than reading it.

You will see this in the first line of the tiering experiment below: before its first call, the function has no code at all.

## Ignition bytecode

Ignition is V8's interpreter. It runs **bytecode**, a compact instruction list for an imagined machine with registers and one special register, the **accumulator**, that most instructions read or write. Here is a small function:

```javascript title="ep_bytecode.mjs"
function area(width, height) {
  const size = width * height;
  return size + 1;
}

console.log(area(3, 4));
```

`--print-bytecode-filter` limits the listing to one function. Memory addresses change on every run, so `sed` replaces them with `0x…` (Node 26.11.1, V8 14.6):

```text frame="terminal"
$ node --print-bytecode --print-bytecode-filter=area ep_bytecode.mjs | sed -E 's/0x[0-9a-f]+/0x…/g'
[generated bytecode for function: area (0x… <SharedFunctionInfo area>)]
Bytecode length: 10
Parameter count 3
Register count 1
Frame size 8
   46 S> 0x… @    0 : 0b 04             Ldar a1
   52 E> 0x… @    2 : 42 03 00          Mul a0, FBV[0]
         0x… @    5 : d2                Star0
   76 S> 0x… @    6 : 4d 01 01          AddSmi [1], FBV[1]
   80 S> 0x… @    9 : b7                Return
Constant pool (size = 0)
Handler Table (size = 0)
Source Position Table (size = 11)
0x… <Other heap object (TRUSTED_BYTE_ARRAY_TYPE)>
13
```

Read the instructions on the right. `a0` and `a1` are the arguments. `Ldar a1` loads `height` into the accumulator, `Mul a0` multiplies it by `width`, `Star0` stores the result in register `r0` (the `size` variable), `AddSmi [1]` adds the small integer 1, and `Return` returns the accumulator. The numbers on the left are source positions. The definitions are in [`bytecodes.h`](https://github.com/v8/v8/blob/14.6.202/src/interpreter/bytecodes.h).

The `FBV[0]` and `FBV[1]` operands are slots in the function's **feedback vector**. Each time `Mul` runs, it records what kinds of values it saw: only small integers so far, or also doubles, strings, objects. That record is how the later tiers know what to optimise for. V8 allocates the vector lazily, after a function has run a few times; the flag `--invocation-count-for-feedback-allocation` defaults to 8 in V8 14.6 ([flag definitions](https://github.com/v8/v8/blob/14.6.202/src/flags/flag-definitions.h)).

## Four tiers

Interpreting is quick to start and slow to run. V8 therefore has three compilers that turn hot functions into machine code, each slower to compile and faster to run than the one before:

| Tier | Kind | What it does |
|---|---|---|
| Ignition | interpreter | runs bytecode and collects feedback |
| Sparkplug | baseline compiler | translates bytecode to machine code without optimising |
| Maglev | optimising compiler | optimises quickly, using the feedback |
| TurboFan | optimising compiler | optimises hardest, for the hottest code |

The descriptions come from the flags `--sparkplug`, `--maglev` and `--turbofan`. On Node 26 all four are on by default. **On Node 22 (V8 12.4) Maglev is off**: `node --v8-options` shows `default: --no-maglev` there, so functions go straight from Sparkplug to TurboFan.

The experiment calls `add` two million times and reports each change of tier. `%ActiveTierIsTurbofan` and its siblings say which code a function is running:

```javascript title="ep_tiers.mjs"
function add(a, b) {
  return a + b;
}

function tier(f) {
  if (%ActiveTierIsTurbofan(f)) return "TurboFan";
  if (%ActiveTierIsMaglev(f)) return "Maglev";
  if (%ActiveTierIsSparkplug(f)) return "Sparkplug";
  if (%ActiveTierIsIgnition(f)) return "Ignition";
  return "not compiled yet";
}
```

The loop records the call number at each change:

```javascript title="ep_tiers.mjs (continued)"
let last = tier(add);
const seen = [last];
for (let i = 1; i <= 2_000_000; i++) {
  add(i, 1);
  const now = tier(add);
  if (now !== last) { seen.push(now + "@" + i); last = now; }
}
console.log(seen.join(" -> "));
```

V8 normally compiles on background threads, so the exact numbers vary between runs. `--single-threaded` makes the run repeatable (Node 26.11.1, V8 14.6):

```text frame="terminal"
$ node --allow-natives-syntax --single-threaded ep_tiers.mjs
not compiled yet -> Ignition@1 -> Sparkplug@21 -> Maglev@411 -> TurboFan@19612
```

Without `--single-threaded`, five runs on my machine gave Maglev between call 1,056 and 2,263, never reached TurboFan for `add` itself, and once skipped Sparkplug. Thresholds are flags too (`--invocation-count-for-maglev` defaults to 400 and `--invocation-count-for-turbofan` to 3000 in V8 14.6), but they are budgets the engine spends down, not exact call counts, as the TurboFan number shows.

### Watching tier-up without natives

`--trace-opt` logs every decision to optimise, and works on any program. Its lines contain addresses, so this command keeps only the text after the function name:

```javascript title="ep_hot.mjs"
function score(word) {
  let total = 0;
  for (const ch of word) total += ch.charCodeAt(0) - 96;
  return total;
}

const words = ["apple", "banana", "cherry", "damson"];
let sum = 0;
for (let i = 0; i < 200_000; i++) sum += score(words[i % 4]);
console.log("sum:", sum);
```

```text frame="terminal"
$ node --trace-opt ep_hot.mjs | grep '^\[marking.*score' | cut -d'>' -f2
 for optimization to MAGLEV, ConcurrencyMode::kConcurrent, reason: hot and stable]
 for optimization to TURBOFAN_JS, ConcurrencyMode::kConcurrent, reason: hot and stable]
```

"Hot and stable" means the function ran often and its feedback stopped changing. The full output also shows **OSR**, on-stack replacement: a long loop can switch to optimised code in the middle of running, without waiting for the next call.

## Deoptimization

Optimised code is a bet on the feedback. If `add` has only ever seen small integers, TurboFan can emit a plain integer addition, plus a check. When the check fails, V8 **deoptimizes**: it throws the optimised code away and continues in the interpreter. The program still gives the right answer; only speed is lost.

`%PrepareFunctionForOptimization` and `%OptimizeFunctionOnNextCall` force TurboFan without waiting:

```javascript title="ep_deopt.mjs"
function add(a, b) {
  return a + b;
}

%PrepareFunctionForOptimization(add);
add(1, 2);
add(3, 4);
%OptimizeFunctionOnNextCall(add);
add(5, 6);
console.log("optimized:", %ActiveTierIsTurbofan(add));

add("5", "6");
console.log("still optimized:", %ActiveTierIsTurbofan(add));
```

The `grep` keeps the program's own lines and the reason from the `--trace-deopt` line (Node 26.11.1, V8 14.6):

```text frame="terminal"
$ node --allow-natives-syntax --trace-deopt ep_deopt.mjs | grep -o -E '^[a-z].*|reason: [^)]*'
optimized: true
reason: not a Smi
still optimized: false
```

A **Smi** is V8's "small integer", stored directly in a pointer-sized word instead of as an object. The strings broke the bet. The feedback now includes strings, so the next optimised version handles both and stays put. One deopt is harmless. A function that deoptimizes again and again, because its inputs keep changing, never stays fast. The next lesson shows the most common cause.

## When engine knowledge should change your code

- **Almost never by itself.** Write clear code, measure, and change only what a profile shows is hot. Tier thresholds, deopt reasons and even whole tiers differ between Node 22 and Node 26; code tuned to one version's quirks can be slower on the next.
- **When a profile says so.** If a hot function keeps deoptimizing (`--trace-deopt` prints the same function many times), look at what varies in its inputs.
- **When you read benchmarks.** A benchmark that runs a function a hundred times measures Ignition and Sparkplug; one that runs it a million times measures TurboFan. [Measuring performance](../measuring-performance/) builds on this.

## Common pitfalls

- **Shipping natives syntax.** `%` functions are V8 test hooks. Keep them in experiments.
- **Treating one trace as the truth.** Background compilation changes the timing on every run. Use `--single-threaded` when you need repeatable output, and remember it is not how production runs.
- **Assuming every Node has the same tiers.** Node 22 runs without Maglev by default.
- **Reading call counts as thresholds.** Tier-up depends on budgets, function size and loops, not a fixed number of calls.

## Exercises

<Exercise title="Warm-up in batches">

Write `isPrime(n)` with a trial-division loop, and call it on 0, 1, 2 and so on. After 10, 100, 1,000, 10,000 and 100,000 calls in total, print the tier it is running in. Run it with `--allow-natives-syntax --single-threaded`. On Node 26.11.1 the expected output is Ignition, Sparkplug, Maglev, then TurboFan twice.

<Solution>

```javascript title="ep_ex_warmup.mjs"
function isPrime(n) {
  for (let d = 2; d * d <= n; d++) if (n % d === 0) return false;
  return n > 1;
}

function tier(f) {
  if (%ActiveTierIsTurbofan(f)) return "TurboFan";
  if (%ActiveTierIsMaglev(f)) return "Maglev";
  if (%ActiveTierIsSparkplug(f)) return "Sparkplug";
  return "Ignition";
}

let calls = 0;
for (const batch of [10, 100, 1000, 10_000, 100_000]) {
  while (calls < batch) isPrime(calls++);
  console.log(`after ${batch} calls: ${tier(isPrime)}`);
}
```

```text frame="terminal"
$ node --allow-natives-syntax --single-threaded ep_ex_warmup.mjs
after 10 calls: Ignition
after 100 calls: Sparkplug
after 1000 calls: Maglev
after 10000 calls: TurboFan
after 100000 calls: TurboFan
```

A benchmark of the first 100 calls would have timed the interpreter and the baseline compiler, not the code that runs in a long-lived server.

</Solution>

</Exercise>

<Exercise title="Count the returns">

Write `clamp(x, low, high)` with two early `if` returns and a final `return x`, call it once, and print its bytecode. Predict how many `Return` instructions it contains, then check with `grep -c Return`. The expected answer is 3.

<Solution>

```javascript title="ep_ex_clamp.mjs"
function clamp(x, low, high) {
  if (x < low) return low;
  if (x > high) return high;
  return x;
}

console.log(clamp(15, 0, 10));
```

```text frame="terminal"
$ node --print-bytecode --print-bytecode-filter=clamp ep_ex_clamp.mjs | grep -c Return
3
```

Each `return` statement becomes its own `Return`, reached through `TestLessThan`, `TestGreaterThan` and `JumpIfFalse` instructions. Bytecode follows the shape of the source closely; the optimising tiers are where the shape changes.

</Solution>

</Exercise>

<Exercise title="Deoptimize, then reoptimize">

Write `half(n)` that returns `n / 2`. Force TurboFan with numbers, call it with the string `"10"`, then force TurboFan again and call it with `"12"`. Print the tier after each step and the deopt reason. The expected output is `true`, the reason `not a Number or Oddball`, `false`, `true`, `true`.

<Solution>

An **Oddball** is V8's name for `undefined`, `null`, `true` and `false`.

```javascript title="ep_ex_reopt.mjs"
function half(n) {
  return n / 2;
}

function optimize() {
  %PrepareFunctionForOptimization(half);
  half(8);
  half(9);
  %OptimizeFunctionOnNextCall(half);
  half(10);
}

optimize();
console.log("optimized for numbers:", %ActiveTierIsTurbofan(half));
half("10");
console.log("after a string:", %ActiveTierIsTurbofan(half));
optimize();
console.log("optimized again:", %ActiveTierIsTurbofan(half));
half("12");
console.log("string again:", %ActiveTierIsTurbofan(half));
```

```text frame="terminal"
$ node --allow-natives-syntax --trace-deopt ep_ex_reopt.mjs | grep -o -E '^[a-z].*|reason: [^)]*'
optimized for numbers: true
reason: not a Number or Oddball
after a string: false
optimized again: true
string again: true
```

The second optimised version was compiled with feedback that includes strings, so `"12"` no longer breaks its assumptions.

</Solution>

</Exercise>

## Summary

- V8 pre-parses most functions and compiles them to bytecode on their first call.
- Ignition runs bytecode built around an accumulator, and records type feedback in a feedback vector.
- Hot functions move up to Sparkplug (baseline), Maglev and TurboFan (optimising). Node 22 has no Maglev by default.
- Optimised code bets on the feedback. A failed check deoptimizes back to the interpreter.
- `--trace-opt`, `--trace-deopt` and `--print-bytecode` work on any program; `%` natives need `--allow-natives-syntax` and belong only in experiments.
