Much of the software you use every day is a command-line tool: `git`, `npm`, `node` itself. They share a small set of conventions that make them work together in pipelines and scripts, and a JavaScript program can follow the same conventions. A well-behaved tool does four things:

- it takes **arguments**: flags such as `-i`, options such as `--max=5`, and plain values such as file names;
- it writes its **results** to *standard output* (stdout) and its **complaints** to *standard error* (stderr), so the two can be separated;
- it may read *standard input* (stdin), so that other programs can feed it;
- it ends with an **exit code**: `0` for success, anything else for failure. The shell, `make`, CI systems and other programs depend on it. The [tools of the trade](../../../fundamentals/beginner/tools-of-the-trade/) lesson introduced the terminal side of this.

You already know the raw material from [the runtime lesson](../node-runtime/): `process.argv`, `process.exitCode` and the `exit` event. This lesson adds the helpers that make tools pleasant to write.

## Arguments with util.parseArgs

`process.argv.slice(2)` is a list of strings, and parsing it by hand quickly turns into a pile of `if` statements. `util.parseArgs` does it from a description of the options you accept. By default it reads `process.argv`; the examples here pass an `args` array so that the result is the same every time.

```javascript title="ct_parseargs.mjs"
import { parseArgs } from "node:util";

const options = {
  verbose: { type: "boolean", short: "v" },
  max: { type: "string", short: "m", default: "10" },
  tag: { type: "string", multiple: true },
};
const argv = ["-v", "--max=5", "build", "--tag", "a", "--tag", "b", "src"];
const { values, positionals } = parseArgs({
  args: argv,
  options,
  allowPositionals: true,
});

console.log(values.verbose, values.max, values.tag);
console.log(positionals);
```

```text
true 5 [ 'a', 'b' ]
[ 'build', 'src' ]
```

- Every option has a `type`, either `"boolean"` (a switch) or `"string"` (takes a value). `short` adds a one-letter alias, so `-v` means `--verbose`. A string option accepts both `--max=5` and `--max 5`.
- `default` supplies a value when the option is absent. Defaults are strings for string options, and `parseArgs` never converts: `values.max` is `"5"`, and turning it into a number is your job.
- `multiple: true` collects every occurrence into an array.
- Anything that is not an option is a **positional** argument. They are accepted only when you pass `allowPositionals: true`.
- A lone `--` ends the options, so that `-- -v` is treated as the positional text `-v`.

By default parsing is **strict**: unknown options, a missing value, or an unexpected positional all throw. The error has a `code` and a readable message, which is what you want to show the user instead of a stack trace.

```javascript title="ct_parseargs.mjs (continued)"
for (const args of [["--nope"], ["--max"], ["extra"]]) {
  try {
    parseArgs({ args, options });
  } catch (error) {
    console.log(error.code, "|", error.message);
  }
}
```

```text
ERR_PARSE_ARGS_UNKNOWN_OPTION | Unknown option '--nope'
ERR_PARSE_ARGS_INVALID_OPTION_VALUE | Option '-m, --max <value>' argument missing
ERR_PARSE_ARGS_UNEXPECTED_POSITIONAL | Unexpected argument 'extra'. This command does not take positional arguments
```

One detail is easy to trip over: the `values` object has no prototype (`Object.getPrototypeOf(values)` is `null`). Reading properties works as usual, but it has no `hasOwnProperty` or `toString`, and `console.log(values)` prints a `[Object: null prototype]` label. Read the properties you need.

## Running other programs

A tool often needs to run another program: a formatter, `git`, or another Node script. The `node:child_process` module starts **child processes**. The three functions below cover almost everything, and each one takes the program and an **array of arguments**, so nothing is passed through a shell.

`spawnSync` runs the program, waits for it to end and returns everything at once. It blocks your program while it waits, which is fine in a short script and wrong in a server. The program to run here is `process.execPath`, the path of the very `node` that is running us, so the example does not depend on any other program being installed.

```javascript title="ct_child.mjs"
import { spawnSync } from "node:child_process";

const script = "console.log('out'); console.error('err'); process.exitCode = 2";
const args = ["-e", script];
const result = spawnSync(process.execPath, args, { encoding: "utf8" });

console.log(result.status, result.signal);
console.log(JSON.stringify(result.stdout), JSON.stringify(result.stderr));
```

```text
2 null
"out\n" "err\n"
```

`-e` tells Node to run the text that follows as a program. The result has the exit `status` (here `2`), the `signal` that killed it if any (here `null`), and the captured `stdout` and `stderr`. Without `encoding: "utf8"` you would get `Buffer` objects.

In a program that must stay responsive, use `execFile`, which takes a callback. As [the callbacks lesson](../callbacks/) showed, `util.promisify` turns that into a function that returns a promise. It resolves with `{ stdout, stderr }` when the exit code is `0`, and **rejects** otherwise.

```javascript title="ct_execfile.mjs"
import { execFile } from "node:child_process";
import { promisify } from "node:util";

const run = promisify(execFile);

const ok = await run(process.execPath, ["-p", "6 * 7"]);
console.log(ok.stdout.trim(), JSON.stringify(ok.stderr));

try {
  const script = "console.log('partial'); process.exit(3)";
  await run(process.execPath, ["-e", script]);
} catch (error) {
  console.log(error.code, error.stdout.trim());
}
try {
  await run("no-such-program-xyz", []);
} catch (error) {
  console.log(error.code);
}
```

```text
42 ""
3 partial
ENOENT
```

For a failure, `error.code` is the exit status as a number (`3`), and the output that the child produced before it stopped is still on the error. If the program cannot even be started, the code is the text `"ENOENT"`, just like a missing file. Keep these two cases apart in your error handling.

`execFile` collects all the output in memory and gives it to you at the end. For long-running programs, or for feeding data in while they run, use `spawn`. It returns at once with a `child` object whose `stdin`, `stdout` and `stderr` are **streams**, and a stream can be read with `for await`, as in [the async iteration lesson](../async-iteration/). The next lesson is all about streams.

```javascript title="ct_spawn.mjs"
import { spawn } from "node:child_process";
import { once } from "node:events";

const script = "process.stdin.pipe(process.stdout)";
const child = spawn(process.execPath, ["-e", script]);
const closed = once(child, "close");

child.stdin.end("piped in\n");
child.stdout.setEncoding("utf8");
let text = "";
for await (const chunk of child.stdout) text += chunk;

const [code, signal] = await closed;
console.log(JSON.stringify(text), code, signal);
```

```text
"piped in\n" 0 null
```

The child copies its input to its output. We write one line to its `stdin` and close it with `end`, then collect the `stdout` chunks as they arrive. The `close` event fires after the process has ended and its streams are done, and `once` turns an event into a promise whose value is the list of the event's arguments. We create that promise **before** we start reading, so the event cannot be missed.

One warning applies to everything in this section. Do not build a command line by joining text, and do not use `exec` (which hands a whole string to a shell) with input that came from a user. A file name such as `a; rm -rf ~` would be run as two commands. With `execFile` and `spawn`, each argument is passed as it is, and no shell interprets it.

## Exit codes

A program's exit code is how the world learns whether it worked. There are five usual ways for a program to end, and the example below runs one child process for each to show the status the parent sees.

```javascript title="ct_exit.mjs"
import { spawnSync } from "node:child_process";

const programs = {
  "falls off the end": "console.log('done')",
  "sets exitCode": "process.exitCode = 5",
  "calls process.exit": "process.exit(4); console.log('never')",
  "throws": "throw new Error('boom')",
  "rejects": "Promise.reject(new Error('late'))",
};
for (const [name, code] of Object.entries(programs)) {
  const args = ["-e", code];
  const { status } = spawnSync(process.execPath, args, { encoding: "utf8" });
  console.log(`${status}  ${name}`);
}
```

```text
0  falls off the end
5  sets exitCode
4  calls process.exit
1  throws
1  rejects
```

- Reaching the end of the script means `0`.
- `process.exitCode = n` records the code and lets the program finish its work, so pending output is not lost. This is the right way to report failure.
- `process.exit(n)` ends the program on the spot. Output that is still being written may be lost, so use it only for a quick exit.
- An uncaught exception and an unhandled promise rejection both end the program with `1`, as [the async errors lesson](../async-errors/) explained.

Conventions: `0` is success, `1` is a general failure. Many tools use `2` for "you used me wrongly". `grep` uses `0` for "found something", `1` for "found nothing" and `2` for an error, and the tool below follows that.

## Reading standard input

When a tool is used in a pipeline, as in `cat notes.txt | node shout.mjs`, its input arrives on `process.stdin`. The `readline` module turns that stream into lines, and the interface can be read with `for await`. The loop ends when the input ends.

```javascript title="ct_stdin.mjs"
import { createInterface } from "node:readline/promises";

const lines = createInterface({ input: process.stdin });
let count = 0;
for await (const line of lines) {
  count++;
  console.log(`${count}: ${line.toUpperCase()}`);
}
console.error(`${count} lines read`);
```

```text
1: HELLO
2: NODE WORLD
```

For this listing the input was the two lines `hello` and `node world`. The summary goes to `console.error`, which writes to stderr, so it did not appear in the output above and would not pollute a pipeline such as `... | node ct_stdin.mjs > out.txt`; in your terminal you would still see it. If you run the program with no pipe at all, it waits for you to type, and you end the input with `Ctrl+D`.

The rule of thumb: **data goes to stdout; progress, warnings and errors go to stderr.** `console.log` writes to stdout and `console.error` to stderr.

## Project: a tiny grep

Here is a complete tool that prints the lines of files that contain some text. It supports `-i` (ignore case) and `-n` (show line numbers), and exits with `0`, `1` or `2` as `grep` does. The tool is in a file called `ct_grep.mjs`. Its first line is a **shebang**, which we come back to at the end. The code is organised as a `main` function that returns the exit code, and the last line of the file turns it into the process exit code.

```javascript title="ct_grep.mjs"
#!/usr/bin/env node
import { parseArgs } from "node:util";
import { readFile } from "node:fs/promises";

const options = {
  "ignore-case": { type: "boolean", short: "i" },
  "line-numbers": { type: "boolean", short: "n" },
};

function parse(argv) {
  try {
    return parseArgs({ args: argv, options, allowPositionals: true });
  } catch (error) {
    console.error(`grep: ${error.message}`);
    return null;
  }
}
```

The `parse` function turns a bad command line into a clean message and `null`. The main part reads the files and prints the matching lines.

```javascript title="ct_grep.mjs (continued)"
async function main(argv) {
  const parsed = parse(argv);
  if (parsed === null) return 2;
  const [pattern, ...files] = parsed.positionals;
  if (pattern === undefined || files.length === 0) {
    console.error("usage: ct_grep [-i] [-n] pattern file...");
    return 2;
  }
  const ignoreCase = parsed.values["ignore-case"];
  const needle = ignoreCase ? pattern.toLowerCase() : pattern;
  let found = false;
  for (const file of files) {
    let text;
    try {
      text = await readFile(file, "utf8");
    } catch (error) {
      console.error(`grep: ${file}: ${error.code}`);
      return 2;
    }
```

Reading can fail, so the error is turned into a message with the error code. Now the matching and the printing.

```javascript title="ct_grep.mjs (continued)"
    text.split("\n").forEach((line, index) => {
      const hay = ignoreCase ? line.toLowerCase() : line;
      if (!hay.includes(needle)) return;
      found = true;
      const where = files.length > 1 ? `${file}:` : "";
      const number = parsed.values["line-numbers"] ? `${index + 1}:` : "";
      console.log(`${where}${number}${line}`);
    });
  }
  return found ? 0 : 1;
}

process.exitCode = await main(process.argv.slice(2));
```

The best way to test a command-line tool is to run it the way a user would, as a child process, and look at its output and exit status. The next program does that. It creates two small files in a temporary directory, runs the tool in that directory so that the file names are short, and prints what came back. (It uses the helper `withTempDir` from [the files lesson](../files-and-paths/), saved as `fp_helper.mjs`.)

```javascript title="ct_run.mjs"
import { spawnSync } from "node:child_process";
import { writeFile } from "node:fs/promises";
import { join } from "node:path";
import { withTempDir } from "./fp_helper.mjs";

const tool = join(import.meta.dirname, "ct_grep.mjs");

await withTempDir(async (dir) => {
  await writeFile(join(dir, "fruit.txt"), "apple\nBanana\ncherry\napple pie\n");
  await writeFile(join(dir, "more.txt"), "pineapple\nplum\n");

```

The function `grep` runs the tool with some arguments and prints the exit status, then what the tool wrote to stdout and to stderr.

```javascript title="ct_run.mjs (continued)"
  function grep(...args) {
    const options = { cwd: dir, encoding: "utf8" };
    const run = spawnSync(process.execPath, [tool, ...args], options);
    console.log(`$ grep ${args.join(" ")}  -> exit ${run.status}`);
    const lines = (text) => text.split("\n").filter(Boolean);
    for (const line of lines(run.stdout)) console.log(line);
    for (const line of lines(run.stderr)) console.log("stderr:", line);
  }

  grep("apple", "fruit.txt");
  grep("-in", "BANANA", "fruit.txt");
  grep("apple", "fruit.txt", "more.txt");
  grep("zzz", "fruit.txt");
  grep("apple", "missing.txt");
  grep("apple");
});
```

```text
$ grep apple fruit.txt  -> exit 0
apple
apple pie
$ grep -in BANANA fruit.txt  -> exit 0
2:Banana
$ grep apple fruit.txt more.txt  -> exit 0
fruit.txt:apple
fruit.txt:apple pie
more.txt:pineapple
$ grep zzz fruit.txt  -> exit 1
$ grep apple missing.txt  -> exit 2
stderr: grep: missing.txt: ENOENT
$ grep apple  -> exit 2
stderr: usage: ct_grep [-i] [-n] pattern file...
```

Each case shows one behaviour. A single file prints bare lines. Several files get a `file:` prefix. No match gives exit `1` and no output. The missing file and the missing arguments give exit `2` with a message on stderr. An unknown option would too, through the `parse` function. This is also how you would test a tool automatically, as the testing lessons later in this module do.

## Making it executable

The first line of `ct_grep.mjs`, `#!/usr/bin/env node`, is a **hashbang** (or shebang) line. On Linux and macOS, if the file is marked executable, the system reads that line to find out which program should run it, so you can type `./ct_grep.mjs -i apple fruit.txt` without writing `node`. JavaScript itself accepts the line as a comment at the very start of a file; that has been part of the language since ES2023.

```bash
chmod +x ct_grep.mjs
./ct_grep.mjs -n apple fruit.txt
```

To install a tool under a command name, a package lists it in the `"bin"` field of its `package.json`. When someone installs the package, npm links that name onto their command path (on Windows it creates a small wrapper, since there is no shebang support).

```json
{
  "name": "ct-grep",
  "version": "1.0.0",
  "type": "module",
  "bin": { "ct-grep": "./ct_grep.mjs" }
}
```

During development, `npm link` in the package folder makes the `ct-grep` command available on your machine. The [npm lesson](../npm-in-depth/) covers `package.json` further.

## Common pitfalls

- **Printing errors with `console.log`.** They end up in the output of a pipeline. Use `console.error`.
- **Always exiting `0`.** A tool that reports failure only in text cannot be used in a script.
- **Calling `process.exit()` right after printing a lot.** Set `process.exitCode` and return.
- **Forgetting that option values are strings.** `--max=5` gives `"5"`.
- **Passing user input to `exec`.** Use `execFile` or `spawn` with an argument array.
- **Using `spawnSync` or `execFileSync` in a server.** They block the event loop.
- **Showing a stack trace to the user** for a mistake in the command line. Catch the error and print one clear line.

<Exercise title="Sum of the numbers on stdin">

Write a program that reads lines from stdin and prints `sum: N`. Blank lines are ignored. A line that is not a number is reported on stderr as `skipped: <line>` and does not count. The input for this exercise is the four lines `3`, `4`, `x` and `10`, followed by a blank line.

Expected output on stdout:

```text

```

<Solution>

`Number("x")` is `NaN`, which `Number.isNaN` detects. The `skipped` message goes to stderr, so it is not part of the output.

```javascript title="ct_ex_sum.mjs"
import { createInterface } from "node:readline/promises";

let sum = 0;
for await (const line of createInterface({ input: process.stdin })) {
  if (line.trim() === "") continue;
  const value = Number(line);
  if (Number.isNaN(value)) {
    console.error(`skipped: ${line}`);
  } else {
    sum += value;
  }
}
console.log(`sum: ${sum}`);
```

```text
sum: 17
```

<Exercise title="A port option">

Write `parseCli(argv)` that accepts `--port N` (short `-p`, default `"3000"`), the switch `--open` and any number of file names. It returns an object `{ port, open, files }` where `port` is a **number**. If the port is not a whole number from 1 to 65535, it throws an `Error` with the message `invalid port: <text>`. Print the result for `["--open", "-p", "8080", "a.txt", "b.txt"]` and the message for `["--port=abc"]`.

Expected output:

```text
{ port: 8080, open: true, files: [ 'a.txt', 'b.txt' ] }
invalid port: abc
```

<Solution>

`parseArgs` supplies strings, so the function converts and validates. Building a fresh object also avoids handing the caller the prototype-less `values`.

```javascript title="ct_ex_port.mjs"
import { parseArgs } from "node:util";

function parseCli(argv) {
  const { values, positionals } = parseArgs({
    args: argv,
    options: {
      port: { type: "string", short: "p", default: "3000" },
      open: { type: "boolean" },
    },
    allowPositionals: true,
  });
  const port = Number(values.port);
  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error(`invalid port: ${values.port}`);
  }
  return { port, open: values.open ?? false, files: positionals };
}

console.log(parseCli(["--open", "-p", "8080", "a.txt", "b.txt"]));
try {
  parseCli(["--port=abc"]);
} catch (error) {
  console.log(error.message);
}
```

```text
{ port: 8080, open: true, files: [ 'a.txt', 'b.txt' ] }
invalid port: abc
```

</Solution>

</Exercise>

<Exercise title="Three programs in parallel">

Using `execFile` with `util.promisify`, run these three programs at the same time: `node -p "1 + 1"`, a program that exits with status `3`, and a program called `no-such-program-xyz`. Wait for all of them with `Promise.allSettled`, and print one line each: `ok: <output>` when it succeeded, `failed (exit N)` when it exited with a status, and `failed (ENOENT)` when it could not start.

Expected output:

```text
ok: 2
failed (exit 3)
failed (ENOENT)
```

<Solution>

For a rejection, the `reason` is the error. A numeric `code` is an exit status, and a text code names a start-up failure.

```javascript title="ct_ex_parallel.mjs"
import { execFile } from "node:child_process";
import { promisify } from "node:util";

const run = promisify(execFile);
const node = process.execPath;

const results = await Promise.allSettled([
  run(node, ["-p", "1 + 1"]),
  run(node, ["-e", "process.exit(3)"]),
  run("no-such-program-xyz", []),
]);

for (const result of results) {
  if (result.status === "fulfilled") {
    console.log("ok:", result.value.stdout.trim());
  } else {
    const code = result.reason.code;
    const text = typeof code === "number" ? `exit ${code}` : code;
    console.log(`failed (${text})`);
  }
}
```

```text
ok: 2
failed (exit 3)
failed (ENOENT)
```

</Solution>

</Exercise>

## Summary

- A command-line tool takes arguments, reads stdin, writes results to stdout and problems to stderr, and ends with an exit code.
- `util.parseArgs` parses flags, options and positionals from a description. Values stay strings, and strict mode throws on bad input.
- Report failure with `process.exitCode`. By convention `0` is success, `1` failure and `2` misuse. Exceptions and unhandled rejections give `1`.
- `readline` over `process.stdin` reads input line by line with `for await`.
- `node:child_process` runs other programs: `spawnSync` (blocking), `execFile` (promise via `promisify`, rejects on non-zero exit) and `spawn` (streams). Pass arguments as an array and avoid `exec` with user input.
- A `#!/usr/bin/env node` line and a `"bin"` entry turn a script into an installable command.
