Suppose you convert a temperature in one place, and a week later you need the same conversion somewhere else. Copying the formula works until you find a mistake in it and have to fix it in six places. A **function** is a named block of code you write once and use as often as you like. It is the main tool for breaking a large problem into small pieces that you can understand, test and reuse one at a time.

## Anatomy of a function

A function has a **name**, a list of **parameters** (the inputs it expects), a **body**, and usually a **return value** (its output).

- A **parameter** is the placeholder name in the definition: `celsius` in `to_fahrenheit(celsius)`.
- An **argument** is the actual value you supply in a call: the `100` in `to_fahrenheit(100)`.

When you call a function, the arguments are matched to the parameters, the body runs, and the call expression is replaced by the returned value. That last point is why you can write `print(to_fahrenheit(100))` or `to_fahrenheit(c) + 1`: a call is an expression.

```text
call:        to_fahrenheit(100)
                  |
                  v   argument 100 is matched to parameter celsius
body:        return celsius * 9 / 5 + 32      ->  212.0
                  |
                  v   the call is replaced by the returned value
use:         print(212.0)
```

## Return versus print

New programmers often mix these up. Printing sends text to the screen for a human to read, and the program cannot use it afterwards. `return` hands a value back to the calling code, which can store it, compute with it or print it. A function that computes should normally **return**, and the caller decides what to do with the result. That makes the function reusable: the same `to_fahrenheit` works in a program that prints, one that draws a chart and one that writes a file.

A function with no `return` statement gives back a special empty value, and the languages handle that differently.

<Tabs>
<Tab label="Python">

def shout(text):
    print(text.upper())


result = shout("hi")
print(result)
```

None
```

A function with no `return` gives back `None`.

## Side effects and pure functions

A **side effect** is any change a function makes beyond returning a value: printing, modifying a global variable, writing a file, changing an argument that was passed in. A **pure function** has none, and its result depends only on its arguments. Call it twice with the same arguments and you get the same answer.

In this program `add` is pure. `add_and_count` returns the same number but also bumps a counter that lives outside the function.

<Tabs>
<Tab label="Python">

```python title="pure_impure.py"
calls = 0


def add(a, b):
    return a + b


def add_and_count(a, b):
    global calls   # lets the function change the outer variable; see the scope lesson
    calls += 1
    return a + b


print(add(2, 3), add(2, 3))
print(add_and_count(2, 3))
print(add_and_count(2, 3))
print("calls:", calls)
```

</Tab>
<Tab label="JavaScript">

```javascript title="pure_impure.js"
let calls = 0;

function add(a, b) {
  return a + b;
}

function addAndCount(a, b) {
  calls += 1;
  return a + b;
}

console.log(add(2, 3), add(2, 3));
console.log(addAndCount(2, 3));
console.log(addAndCount(2, 3));
console.log("calls:", calls);
```

</Tab>
<Tab label="Java">

```java title="PureImpure.java"
public class PureImpure {
    static int calls = 0;

    static int add(int a, int b) {
        return a + b;
    }

    static int addAndCount(int a, int b) {
        calls += 1;
        return a + b;
    }

    public static void main(String[] args) {
        System.out.println(add(2, 3) + " " + add(2, 3));
        System.out.println(addAndCount(2, 3));
        System.out.println(addAndCount(2, 3));
        System.out.println("calls: " + calls);
    }
}
```

</Tab>
<Tab label="C">

```c title="pure_impure.c"

    return a + b;
}

static int add_and_count(int a, int b) {
    calls += 1;
    return a + b;
}

int main(void) {
    printf("%d %d\n", add(2, 3), add(2, 3));
    printf("%d\n", add_and_count(2, 3));
    printf("%d\n", add_and_count(2, 3));
    printf("calls: %d\n", calls);

```

</Tab>
</Tabs>

All four print:

```text

5
5
calls: 2
```

`add` leaves nothing behind. `add_and_count` returns the same number but also changes `calls`, so calling it has a visible effect elsewhere. Neither is wrong; programs need side effects, since printing is one. But pure functions are far easier to test and to reason about, so a good habit is to keep the calculating parts pure and push the printing and file-writing to the edges.

## The call stack

When a function calls another, the first must wait for the second to finish. The computer tracks this with the **call stack**: a pile of **frames**, one per active call, each holding that call's parameters and local variables. A new call pushes a frame on top; a return pops it off and execution resumes in the frame below.

Here three functions call each other in a chain. Each prints a line when it starts and when it ends, indented to show its depth.

<Tabs>
<Tab label="Python">

```python title="call_stack.py"
def outer():
    print("outer starts")
    middle()
    print("outer ends")


def middle():
    print("  middle starts")
    inner()
    print("  middle ends")


def inner():
    print("    inner runs")


outer()
```

</Tab>
<Tab label="JavaScript">

```javascript title="call_stack.js"

  console.log("outer ends");
}

function middle() {
  console.log("  middle starts");
  inner();
  console.log("  middle ends");
}

function inner() {
  console.log("    inner runs");
}

outer();
```

</Tab>
<Tab label="Java">

```java title="CallStack.java"
public class CallStack {
    static void outer() {
        System.out.println("outer starts");
        middle();
        System.out.println("outer ends");
    }

    static void middle() {
        System.out.println("  middle starts");
        inner();
        System.out.println("  middle ends");
    }

    static void inner() {
        System.out.println("    inner runs");
    }

    public static void main(String[] args) {
        outer();
    }
}
```

</Tab>
<Tab label="C">

```c title="call_stack.c"
#include <stdio.h>

static void inner(void) {
    printf("    inner runs\n");
}

static void middle(void) {
    printf("  middle starts\n");
    inner();
    printf("  middle ends\n");
}

static void outer(void) {
    printf("outer starts\n");
    middle();
    printf("outer ends\n");
}

int main(void) {
    outer();
    return 0;
}
```

C needs each function defined before it is called, so the order is reversed: `inner` first, `outer` last.

</Tab>
</Tabs>

All four print:

```text
outer starts
  middle starts
    inner runs
  middle ends
outer ends
```

Here is the stack at five moments. Read each column from the bottom up.

```text
 (1)         (2)         (3)         (4)         (5)
                         inner
             middle      middle      middle
 outer       outer       outer       outer       outer
 main        main        main        main        main
```

In (1) `main` has called `outer`. In (2) `outer` has called `middle`, and in (3) `middle` has called `inner`, the deepest point. When `inner` returns, its frame is removed (4), then `middle`'s (5), and `outer` carries on. This explains the order of the output (`outer starts`, `middle starts`, `inner runs`, `middle ends`, `outer ends`) and, later, what a stack trace in an error message is showing you: the pile of frames at the moment something went wrong.

## Designing good functions

- **Do one thing.** If you struggle to name it without using "and", split it.
- **Name it for what it does:** `to_fahrenheit`, not `convert` or `func1`.
- **Keep the inputs explicit.** Pass in what the function needs rather than having it reach for global variables.
- **Prefer returning to printing,** as described above.
- **Keep it short enough to read at a glance.** There is no magic number, but if you must scroll, look for a piece to extract.

## Common pitfalls

- **Printing instead of returning,** then trying to use the result and finding it empty (`None` or `undefined`).
- **Forgetting the parentheses.** `to_fahrenheit` refers to the function; `to_fahrenheit(100)` calls it.
- **Mismatched argument counts or order.** `report("Ana", scores)` and `report(scores, "Ana")` are different calls.
- **Expecting a function to change your variable.** In most languages numbers and strings passed in are copies; reassigning the parameter inside does not affect the caller. (More on this in the memory lesson later in the track.)
- **Code after `return` that never runs.** `return` ends the function immediately.
- **Hidden dependencies.** A function that quietly reads a global behaves differently depending on something not visible in its call.

## Summary

- A function is a named, reusable block with parameters (placeholders) that receive arguments (actual values).
- Return a value from a computing function and let the caller decide whether to print it.
- Side effects are changes beyond the return value; pure functions have none and are easiest to test.
- Calls form a stack of frames: the most recent call finishes first.
