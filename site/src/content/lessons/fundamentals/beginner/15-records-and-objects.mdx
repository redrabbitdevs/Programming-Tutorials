A library book has a title, an author, a year and a flag saying whether it is on the shelf. You could keep those in four parallel lists and hope the positions always line up, or in a map with string keys and hope nobody misspells one. Neither is a good fit. What you want is a single value that groups the pieces, gives each a name, and has a recognisable shape. That is a **record**.

## Records: named fields

A **record** (also called a *struct*, or a *data class*) is a value made of several **fields**, each with a name and often its own type. You make one by filling in all the fields, and you read or change a field by its name, usually with a dot: `book.title`.

Unlike a list, whose elements normally share one meaning ("a score, another score"), a record's fields are different things that belong together: a title, a year, a flag. Unlike a map, a record's fields are fixed in advance, so a typo in a field name is caught early instead of silently creating a new key.

```text
Book
+-----------+-----------------+
| title     | "Dune"          |
| author    | "Frank Herbert" |
| year      | 1965            |
| available | true            |
+-----------+-----------------+
```

## From records to objects

A record only holds data. Sooner or later you write functions that work on that data: describe a book, lend it out. The step from record to **object** is to keep those functions with the data they operate on, as **methods**. You call a method on a particular object: `book.lend()`. Inside, the method has access to that object's fields (Python calls it `self`, JavaScript and Java call it `this`; in C there are no methods, so you pass a pointer to the struct as the first parameter instead).

A **class** (or, in C, a struct type plus its functions) is the blueprint: it says which fields every book has and which methods it supports. Each book you create from it is an **instance**.

A few things to notice:

- The Python version is a `dataclass`, a shortcut that writes the constructor for you from the field list. JavaScript and Java spell the constructor out.
- Java and C declare the type of every field. Python's annotations (`title: str`) document the type; JavaScript has none at all.
- The C function receives a pointer (`b->title` is the field of the struct `b` points at). It needs a `Book *`, not a `Book`, so that `book_lend` changes the original instead of a copy. Pointers are covered in [memory and references](../memory-and-references/).

## Encapsulation: protecting the data

If any code anywhere may set any field, then any code anywhere may break your rules. A library member, for instance, may borrow at most two books at once. If other code can simply append to the member's list of books, that rule will be broken sooner or later.

**Encapsulation** means a type keeps its fields private and offers a small set of methods as the only way to change them. The methods enforce the rules. Callers then depend on what the object *does*, not on how it stores things, so you are free to change the inside later.

Languages support this differently. Java has `private` fields. JavaScript has `#name` private fields. Python has no enforcement, only a convention: a leading underscore (`_borrowed`) means "internal, please leave alone". C can hide a struct's layout by keeping its definition out of the header file. The idea is the same everywhere. In each program below, Ada borrows two books, is refused a third, returns one, and then borrows the third.

```python title="encapsulation_demo.py"
class Member:
    MAX_BOOKS = 2

    def __init__(self, name):
        self.name = name
        self._borrowed = []          # internal: use borrow() and give_back()

    def borrow(self, title):
        if len(self._borrowed) >= self.MAX_BOOKS:
            raise ValueError(f"{self.name} already has {self.MAX_BOOKS} books")
        self._borrowed.append(title)

    def give_back(self, title):
        self._borrowed.remove(title)

    def books(self):
        return list(self._borrowed)  # a copy, so callers cannot change ours


ada = Member("Ada")
ada.borrow("Dune")
ada.borrow("Emma")
try:
    ada.borrow("Ulysses")
except ValueError as err:
    print("refused:", err)

ada.give_back("Dune")
ada.borrow("Ulysses")
print("books:", ", ".join(ada.books()))
```

```java title="EncapsulationDemo.java"
import java.util.List;

class Member {
    static final int MAX_BOOKS = 2;
    private final String name;
    private final List<String> borrowed = new ArrayList<>();   // private: other classes cannot touch it

        this.name = name;
```

```c title="encapsulation_demo.c"
#include <stdio.h>
#include <string.h>

#define MAX_BOOKS 2

/* In a real project this struct would be declared in a header as an incomplete
   type, so other files could not see the fields at all. */
typedef struct {
    const char *name;
    const char *borrowed[MAX_BOOKS];
    int count;
} Member;

/* Returns 0 on success, -1 when the member already has the maximum. */
static int member_borrow(Member *m, const char *title) {
    if (m->count >= MAX_BOOKS) {
        return -1;
    }
    m->borrowed[m->count++] = title;
    return 0;
}

static void member_give_back(Member *m, const char *title) {
    for (int i = 0; i < m->count; i++) {
        if (strcmp(m->borrowed[i], title) == 0) {
            m->borrowed[i] = m->borrowed[m->count - 1];   /* fill the gap with the last book */
            m->count--;
            return;
        }
    }
}

static void member_print_books(const Member *m) {
    printf("books: ");
    for (int i = 0; i < m->count; i++) {
        printf("%s%s", i > 0 ? ", " : "", m->borrowed[i]);
    }
    printf("\n");
}

int main(void) {
    Member ada = {"Ada", {NULL}, 0};
    member_borrow(&ada, "Dune");
    member_borrow(&ada, "Emma");
    if (member_borrow(&ada, "Ulysses") != 0) {
        printf("refused: %s already has %d books\n", ada.name, MAX_BOOKS);
    }

    member_give_back(&ada, "Dune");
    member_borrow(&ada, "Ulysses");
    member_print_books(&ada);
    return 0;
}
```

## Identity versus equality

Two questions that sound alike are different:

- **Equality**: do these two things hold the same contents?
- **Identity**: are these two names for the very same object in memory?

Two copies of the same paperback are equal in contents, but they are two separate objects. Lend one and the other stays on the shelf. If instead two variables name one object, lending through either changes what both see.

```text
a ---> [ "Dune", 1965 ]        b ---> [ "Dune", 1965 ]     a and b: equal, not identical
c ---> (same object as a)                                  a and c: identical
```

```javascript title="identity_demo.js"
        this.year = year;
```

```c title="identity_demo.c"
#include <stdio.h>
#include <string.h>

typedef struct {
    const char *title;
    int year;
} Book;

/* C has no built-in == for structs, so equality is a function we write. */
static int book_equals(const Book *x, const Book *y) {
    return strcmp(x->title, y->title) == 0 && x->year == y->year;
}

int main(void) {
    Book a = {"Dune", 1965};
    Book b = {"Dune", 1965};
    Book *c = &a;   /* a second name for a: a pointer to it */

    printf("equal contents: %s\n", book_equals(&a, &b) ? "yes" : "no");
    printf("same object (a, b): %s\n", &a == &b ? "yes" : "no");
    printf("same object (a, c): %s\n", &a == c ? "yes" : "no");

    c->year = 1966;
    printf("a.year after changing c: %d\n", a.year);
    printf("b.year: %d\n", b.year);
    return 0;
}
```

`c = a` did not make a new book. It gave the same book a second name, so changing the year through `c` is visible through `a`, while `b`, a separate object, is untouched. Python's `is`, JavaScript's `===` on objects and Java's `==` on objects all test identity; in C you compare addresses. For equality, Python's dataclass writes `==` for you, while JavaScript, Java and C need a method or function you define yourself (and Java's `hashCode` must agree with `equals`, so maps and sets that use it keep working).

C structs are plain values, copied byte by byte on assignment, so `Book c = a;` would make a true copy there. That is why the C program makes `c` a pointer when it wants a second name for the same book.

## Common pitfalls

- **Parallel lists** (`titles[i]`, `authors[i]`) that drift out of step. Use one record per item and a single list of records.
- **Public fields everywhere,** so any code can put an object into an invalid state. Funnel changes through methods.
- **Confusing `==` with identity.** In Java, `a == b` on two objects asks "same object?", not "same contents?". Use `equals`.
- **Aliasing surprises.** After `c = a`, a change through `c` shows up in `a`. Copy deliberately when you need independence.
- **Putting everything in one giant object** that does ten unrelated jobs. A good type has one clear purpose.

```python title="library.py"
        self.title = title
        self.author = author
        self.available = True

    MAX_BOOKS = 2

    def __init__(self, name):
        self.name = name
        self._borrowed = []

    def borrow(self, book):
        if not book.available:
            raise ValueError(f"{book.title!r} is already on loan")
        if len(self._borrowed) >= self.MAX_BOOKS:
            raise ValueError(f"{self.name} already has {self.MAX_BOOKS} books")
```

```java title="Library.java"
import java.util.List;

class Book {
    final String title;
    final String author;
    boolean available = true;

    Book(String title, String author) {
        this.title = title;
        this.author = author;
    }
}

class Member {
    static final int MAX_BOOKS = 2;
    private final String name;
    private final List<Book> borrowed = new ArrayList<>();

    Member(String name) {
        this.name = name;
    }

    void borrow(Book book) {
        if (!book.available) {
            throw new IllegalStateException("'" + book.title + "' is already on loan");
        }
        if (borrowed.size() >= MAX_BOOKS) {
            throw new IllegalStateException(name + " already has " + MAX_BOOKS + " books");
        }
        book.available = false;
        borrowed.add(book);
    }

    void giveBack(Book book) {
        borrowed.remove(book);
        book.available = true;
    }

    String titles() {
        List<String> names = new ArrayList<>();
        for (Book book : borrowed) {
            names.add(book.title);
        }
        return String.join(", ", names);
    }
}
```

```c title="library.c"
#include <stdbool.h>
#include <stdio.h>

#define MAX_BOOKS 2

typedef struct {
    const char *title;
    const char *author;
    bool available;
} Book;

typedef struct {
    const char *name;
    Book *borrowed[MAX_BOOKS];
    int count;
} Member;

/* Returns NULL on success, or a message that says why the loan was refused. */
static const char *member_borrow(Member *m, Book *book) {
    static char message[80];
    if (!book->available) {
        snprintf(message, sizeof message, "'%s' is already on loan", book->title);
        return message;
    }
    if (m->count >= MAX_BOOKS) {
        snprintf(message, sizeof message, "%s already has %d books", m->name, MAX_BOOKS);
        return message;
    }
    book->available = false;
    m->borrowed[m->count++] = book;
    return NULL;
}

static void member_give_back(Member *m, Book *book) {
    for (int i = 0; i < m->count; i++) {
        if (m->borrowed[i] == book) {
            m->borrowed[i] = m->borrowed[m->count - 1];
            m->count--;
            book->available = true;
            return;
        }
    }
}

static void member_print(const Member *m) {
    printf("%s: ", m->name);
    for (int i = 0; i < m->count; i++) {
        printf("%s%s", i > 0 ? ", " : "", m->borrowed[i]->title);
    }
    printf("\n");
}

int main(void) {
    Book dune = {"Dune", "Frank Herbert", true};
    Book emma = {"Emma", "Jane Austen", true};
    Book ulysses = {"Ulysses", "James Joyce", true};
    Member ada = {"Ada", {NULL}, 0};
    Member grace = {"Grace", {NULL}, 0};

    member_borrow(&ada, &dune);
    member_borrow(&ada, &emma);

    Member *members[] = {&ada, &grace};
    Book *books[] = {&ulysses, &dune};
    for (int i = 0; i < 2; i++) {
        const char *problem = member_borrow(members[i], books[i]);
        if (problem != NULL) {
            printf("refused: %s\n", problem);
        }
    }
```

<Exercise title="Spot the design problem">

A `Temperature` object stores `celsius` as a public field. Another part of the program sets `t.celsius = -500`. What is wrong, and how would you fix the design? Then check your fix: setting 20 should be accepted, and setting -500 should be refused with the message `rejected: -500 is below absolute zero`.

<Solution>

Nothing stops an impossible value: nothing can be colder than absolute zero (about -273.15 degrees Celsius). Make the field private and offer a setter method that checks the value and refuses it when it is out of range. Then the object can never be in an invalid state, whichever code uses it.

<Tabs>
<Tab label="Python">

```python title="temperature.py"
class Temperature:
    def __init__(self):
        self._celsius = 0.0

    def set_celsius(self, value):
        if value < -273.15:
            raise ValueError(f"{value} is below absolute zero")
        self._celsius = value

    def celsius(self):
        return self._celsius


t = Temperature()
t.set_celsius(20)
print("accepted:", t.celsius())
try:
    t.set_celsius(-500)
except ValueError as err:
    print("rejected:", err)
```

</Tab>

<Tab label="C">

```c title="temperature.c"
#include <stdio.h>

typedef struct {
    double celsius;   /* callers should use temperature_set instead of writing this */
} Temperature;

/* Returns 0 if the value was accepted, -1 if it is below absolute zero. */
static int temperature_set(Temperature *t, double value) {
    if (value < -273.15) {
        return -1;
    }
    t->celsius = value;
    return 0;
}

int main(void) {
    Temperature t = {0};
    if (temperature_set(&t, 20) == 0) {
        printf("accepted: %g\n", t.celsius);
    }
    if (temperature_set(&t, -500) != 0) {
        printf("rejected: -500 is below absolute zero\n");
    }
    return 0;
}
```

C cannot force callers to go through `temperature_set`; the protection comes from hiding the struct's layout in a separate file.

## Summary

- A record groups named fields into one value; methods turn it into an object that carries its own behaviour.
- Encapsulation keeps fields private and enforces rules in one place.
- Equality asks whether contents match; identity asks whether two names refer to the same object.
