Finding things and putting them in order are two of the oldest jobs in computing, and they are closely linked: ordering data is mostly what makes it fast to search. They are also where the growth rates from the [previous lesson](../big-o/) first pay off in practice.

## Searching

**Searching** means finding where a value sits in a collection, or learning that it is absent. We will have each search return the **index** of the value, or `-1` when it is not there. (A language might instead return a null value or throw an error. Returning `-1` works because no valid index is negative.)

### Linear search

The simplest method is to look at each item in order until you find the target or run out of items.

```text
procedure linear_search(items, target)
    for each position i from 0 to the last
        if items[i] equals target
            return i
    return -1
```

It needs no preparation and works on any list, ordered or not. In the worst case it looks at every item, so it is O(n).

### Binary search

If the list is **already sorted**, you can do much better, the way you find a word in a dictionary: open near the middle, see whether you went too far or not far enough, and discard the half that cannot contain the word. Repeat on what remains.

Searching for 23 in a sorted list of ten numbers, with `low`, `high` and `mid` marking the live range:

| Step | low | high | mid | items[mid] | Decision |
|---|---|---|---|---|---|
| 1 | 0 | 9 | 4 | 16 | 16 < 23, so the target is to the right: low = 5 |
| 2 | 5 | 9 | 7 | 56 | 56 > 23, so the target is to the left: high = 6 |
| 3 | 5 | 6 | 5 | 23 | found at index 5 |

Each probe throws away half of what is left, so the number of probes is the number of halvings: O(log n). For a million sorted items that is about 20 probes instead of up to a million. The price is the precondition: **binary search gives wrong answers on unsorted data**, with no warning.

Both agree, as they must on sorted data. The `mid` line is spelled two ways. `(low + high) / 2` is fine in Python and JavaScript. In Java and C, `int` has a fixed range, and for an array with over a billion items `low + high` can exceed it and wrap to a negative number. Writing `low + (high - low) / 2` computes the same value without that risk. It is the kind of detail that stayed hidden in widely used library code for years.

Binary search is famous for being easy to get nearly right. The usual mistakes are `<` instead of `<=` in the loop condition (missing the last candidate), and `mid` instead of `mid + 1` or `mid - 1` when shrinking the range (an infinite loop). Test it at both ends of the list and with a value that is absent.

## Sorting

**Sorting** puts items in order. Almost every language gives you a fast sort, and in real code you should use it. Writing sorts yourself is still worthwhile, because it is where the ideas of this module meet: loops, invariants, recursion and growth rates, all in a small space.

### Insertion sort

Insertion sort works like arranging playing cards in your hand. Keep the left part of the list sorted. Take the next item, slide larger sorted items one place right to open a gap, and drop the item in.

```text
procedure insertion_sort(items)
    for each position i from 1 to the last
        set current to items[i]
        set j to i - 1
        while j >= 0 and items[j] is greater than current
            move items[j] one place right
            decrease j
        put current into items[j + 1]
```

The code prints the list after each insertion so you can watch the sorted region grow:

How much work is it? In the worst case (a list in reverse order), each new item slides past every item before it, giving `1 + 2 + … + (n − 1)` shifts. That is the same `n(n − 1) / 2` count you met for `pair_steps`, so insertion sort is **O(n²)** in the worst case. On a list that is already sorted, the inner loop never runs, so it is **O(n)**. That makes it a sensible choice for short lists and for lists that are nearly in order, and a poor choice for big, shuffled ones.

### Merge sort

Merge sort uses a different idea, **divide and conquer**: split the list in half, sort each half, then **merge** the two sorted halves into one sorted list. Sorting the halves is the same problem again on smaller input, so you solve it by calling the same procedure, as in the [recursion lesson](../recursion/). A list of zero or one item is already sorted, which is the base case.

```text
              [38, 27, 43, 3]
              /              \
        [38, 27]            [43, 3]
        /      \            /     \
     [38]     [27]       [43]     [3]
        \      /            \     /
        [27, 38]            [3, 43]
              \              /
              [3, 27, 38, 43]
```

The work happens in the merge. Given two sorted lists, repeatedly compare their front items and take the smaller. Each item is taken exactly once, so merging `n` items in total is O(n).

The list can be halved about log n times, and each level of the diagram does O(n) merging in total, so merge sort is **O(n log n)** in every case. It needs O(n) extra space for the merged results, which is the price you pay for the speed.

def merge(left, right):
    result = []
    i = 0
    j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:          # <= keeps equal items in order (stable)
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result


def merge_sort(items):
    if len(items) <= 1:
        return items
    mid = len(items) // 2
    return merge(merge_sort(items[:mid]), merge_sort(items[mid:]))


print(merge_sort([38, 27, 43, 3, 9, 82, 10]))
print(merge_sort([]))
print(merge_sort([7]))

function merge(left, right) {
  const result = [];
  let i = 0;
  let j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) {         // <= keeps equal items in order (stable)
      result.push(left[i]);
      i += 1;
    } else {
      result.push(right[j]);
      j += 1;
    }
  }
  return result.concat(left.slice(i), right.slice(j));
}

function mergeSort(items) {
  if (items.length <= 1) {
    return items;
  }
  const mid = Math.floor(items.length / 2);
  return merge(mergeSort(items.slice(0, mid)), mergeSort(items.slice(mid)));
}

import java.util.Arrays;

public class MergeSortDemo {
    static int[] merge(int[] left, int[] right) {
        int[] result = new int[left.length + right.length];
        int i = 0;
        int j = 0;
        int k = 0;
        while (i < left.length && j < right.length) {
            if (left[i] <= right[j]) {       // <= keeps equal items in order (stable)
                result[k++] = left[i++];
            } else {
                result[k++] = right[j++];
            }
        }
        while (i < left.length) {
            result[k++] = left[i++];
        }
        while (j < right.length) {
            result[k++] = right[j++];
        }
        return result;
    }

    static int[] mergeSort(int[] items) {
        if (items.length <= 1) {
            return items;
        }
        int mid = items.length / 2;
        int[] left = mergeSort(Arrays.copyOfRange(items, 0, mid));
        int[] right = mergeSort(Arrays.copyOfRange(items, mid, items.length));
        return merge(left, right);
    }

    public static void main(String[] args) {
        System.out.println(Arrays.toString(mergeSort(new int[] {38, 27, 43, 3, 9, 82, 10})));
        System.out.println(Arrays.toString(mergeSort(new int[] {})));
        System.out.println(Arrays.toString(mergeSort(new int[] {7})));
    }
}

## Stability

A sort is **stable** if items that compare as equal keep the order they had before sorting. It matters when you sort by more than one criterion. Suppose a list of people is already in name order, and you now sort by age. A stable sort leaves people of equal age in name order, which is usually what you want. An unstable sort may shuffle them.

Both of the sorts above are stable. Insertion sort only shifts items that are strictly greater than the one being inserted (`>`, not `>=`), so equal items never pass each other. Merge sort takes from the left half when the two front items are equal (`<=`), so the earlier item comes out first.

## Built-in sorts

In real programs, call the sort the language provides. It is faster than anything you will write, and well tested. Each of the four handles stability differently, so check before you rely on it:

| Language | Call | Stable? |
|---|---|---|
| Python | `sorted(items, key=...)` or `items.sort()` | Yes, guaranteed |
| JavaScript | `array.sort(compare)` | Yes, guaranteed since ES2019 |
| Java | `Arrays.sort(objects, comparator)` | Yes for objects (the sort for primitive arrays is not, but equal numbers are indistinguishable) |
| C | `qsort` | No promise. Break ties yourself |

#include <stdlib.h>

struct person {
    const char *name;
    int age;
    int original_index;     /* qsort is not guaranteed stable, so we break ties ourselves */
};

static int by_age_then_position(const void *a, const void *b) {
    const struct person *p = a;
    const struct person *q = b;
    if (p->age != q->age) {
        return p->age < q->age ? -1 : 1;
    }
    return p->original_index - q->original_index;
}

        {"Ana", 30, 0}, {"Ben", 25, 1}, {"Cy", 30, 2}, {"Di", 25, 3},

    qsort(people, 4, sizeof people[0], by_age_then_position);

## Common pitfalls

- **Binary search on unsorted data.** It runs without complaint and returns garbage. Sort first, or use linear search.
- **Sorting numbers as text in JavaScript.** `[10, 9, 1].sort()` with no comparator compares items as strings and returns `[1, 10, 9]`. Always pass a comparison such as `(a, b) => a - b`.
- **Mixing up in-place and copying sorts.** Python's `items.sort()` changes the list and returns `None`; `sorted(items)` returns a new list and leaves the original alone. Writing `items = items.sort()` throws your list away.
- **Writing your own sort for production code.** It will be slower and less trustworthy than the standard one.
- **Assuming a sort is stable** without checking the language's guarantee, as with `qsort`.
- **Sorting just to find the smallest or largest item.** A single linear pass is O(n); a full sort is O(n log n).

def binary_search_count(items, target):
    loops = 0
    low = 0
    high = len(items) - 1

        loops += 1
        mid = (low + high) // 2

            return loops
        if items[mid] < target:
            low = mid + 1
        else:

  let loops = 0;
  let low = 0;
  let high = items.length - 1;
  while (low <= high) {

<Exercise title="Count the shifts">

Insertion sort moves a value one place to the right each time it shifts. For the input `[4, 3, 2, 1]` (the worst case), count the total number of shifts across all passes, and compare with the formula `n(n − 1) / 2`.

Expected answer: 6 shifts, matching the formula for n = 4.

<Solution>

| Pass | Item inserted | Values it slides past | Shifts |
|---|---|---|---|
| i = 1 | 3 | 4 | 1 |
| i = 2 | 2 | 4, 3 | 2 |
| i = 3 | 1 | 4, 3, 2 | 3 |

Total: 1 + 2 + 3 = 6, and `4 × 3 / 2 = 6`. For a list of 100,000 reversed items the same formula gives nearly five billion shifts, which is why insertion sort is only for small or nearly sorted input.

## Recap

- Linear search works on any list and costs O(n). Binary search needs a sorted list and costs O(log n), by discarding half the range at each probe.
- Insertion sort is simple, stable, O(n²) in the worst case and O(n) on sorted input. Merge sort splits, sorts and merges recursively, is stable, and is O(n log n) in every case at the cost of extra space.
- A stable sort keeps equal items in their original order, which makes sorting by several keys in turn work.
- In practice, use the built-in sort, and check its stability guarantee and its default comparison (JavaScript's compares as text unless you pass a function).
