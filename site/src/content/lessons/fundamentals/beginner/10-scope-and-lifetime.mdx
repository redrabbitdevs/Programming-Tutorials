In the last lesson a function used its own parameters and variables. But what if two functions both use a variable called `total`? Do they share it? **Scope** is the set of rules that decides which parts of a program can see a given name. Getting it right is what lets a thousand-line program reuse short names like `i` and `result` without chaos.

## Scope: where a name is visible

A name is **in scope** in the region of code where it can be used.

- **Local scope** (function scope): names created inside a function exist only inside it. When the function ends they are gone.
- **Global scope**: names created at the top level of the file are visible everywhere in it, including inside functions (for reading, at least).
- **Block scope**: in some languages, a name created inside a pair of braces, such as an `if` body or a loop body, is visible only within those braces.

When a name is used, the language looks for it in the innermost scope first, then moves outward one level at a time until it finds a match. If nothing matches, you get an error such as `NameError`, `ReferenceError` or "cannot find symbol".

```text
lookup of x inside show():

  show()   ---- has its own x?  yes -> use it, stop
     |
     v  no
  file     ---- has an x?       yes -> use it, stop
     |
     v  no
  error: the name is not defined
```

### Shadowing

If an inner scope creates a variable with the same name as one outside, the inner one **shadows** the outer: inside the function, the name means the local variable, and the outer one is unreachable by that name. Crucially, the outer variable is not changed. They are two different variables that happen to share a label.

<Tabs>
<Tab label="Python">

```python title="scope_basic.py"
x = "global"


def show():
    x = "local"  # a new variable that shadows the outer x
    print("inside:", x)


show()
print("outside:", x)
```

</Tab>
<Tab label="JavaScript">

```javascript title="scope_basic.js"
let x = "global";

function show() {
  let x = "local"; // a new variable that shadows the outer x
  console.log("inside:", x);
}

show();
console.log("outside:", x);
```

</Tab>
<Tab label="Java">

```java title="ScopeBasic.java"
public class ScopeBasic {
    static String x = "global";

    static void show() {
        String x = "local"; // a new variable that shadows the field
        System.out.println("inside: " + x);
    }

    public static void main(String[] args) {
        show();
        System.out.println("outside: " + x);
    }
}
```

</Tab>
<Tab label="C">

```c title="scope_basic.c"
#include <stdio.h>

const char *x = "global";

void show(void) {
    const char *x = "local"; /* a new variable that shadows the global */
    printf("inside: %s\n", x);
}

int main(void) {
    show();
    printf("outside: %s\n", x);
    return 0;
}
```

</Tab>
</Tabs>

All four print:

```text
inside: local
outside: global
```

(Java has no free-standing global variables; the closest equivalent is a `static` field of the class, which is what `x` is here.)

Shadowing is legal but easy to misread. Prefer distinct names unless the reuse is deliberate.

## Block scope: languages disagree

Python has only function scope. A variable created inside an `if` or a loop is still there afterwards. In JavaScript's `let`, Java and C, the variable dies at the closing brace.

<Tabs>
<Tab label="Python">

```python title="scope_block.py"
if True:
    inner = 42
print(inner)
```

```text title="output"
42
```

Python has no block scope, only function scope, so `inner` is still there after the `if`.

</Tab>
<Tab label="JavaScript">

```javascript title="scope_block.js"
if (true) {
  let inner = 42;
}
console.log(typeof inner);
```

```text title="output"
undefined
```

`let` is confined to its block. Using `typeof` on a name that does not exist is the one safe way to ask about it; any other use would throw a `ReferenceError`.

</Tab>
<Tab label="Java">

```java title="ScopeBlock.java"
public class ScopeBlock {
    public static void main(String[] args) {
        if (true) {
            int inner = 42;
            System.out.println(inner);
        }
        // System.out.println(inner);  // would not compile: inner is out of scope
    }
}
```

```text title="output"
42
```

The only legal use of `inner` is inside its block. The commented-out line shows what the compiler would reject.

</Tab>
<Tab label="C">

```c title="scope_block.c"
#include <stdio.h>

int main(void) {
    if (1) {
        int inner = 42;
        printf("%d\n", inner);
    }
    /* printf("%d\n", inner);  would not compile: inner is out of scope */
    return 0;
}
```

```text title="output"
42
```

As in Java, `inner` exists only inside its braces, and the commented-out line would not compile.

</Tab>
</Tabs>

JavaScript has a historical oddity: the older `var` keyword is function-scoped, not block-scoped, like Python. Modern code uses `let` and `const`, which are block-scoped.

## Assigning to a global from inside a function

Reading a global from a function is fine. Assigning is where the languages differ. In JavaScript, Java and C, an assignment to a name that has no local declaration changes the global. In Python, an assignment inside a function creates a new local variable unless you say otherwise.

<Tabs>
<Tab label="Python">

```python title="scope_global.py"
counter = 0


def increment():
    global counter  # without this line, "counter += 1" raises UnboundLocalError
    counter += 1


increment()
increment()
print(counter)
```

Without the `global` line, `counter += 1` would fail, since Python sees that the function assigns to `counter`, decides it is local, and finds it has no value yet.

</Tab>
<Tab label="JavaScript">

```javascript title="scope_global.js"
let counter = 0;

function increment() {
  counter += 1;   // no local declaration, so this changes the global
}

increment();
increment();
console.log(counter);
```

</Tab>
<Tab label="Java">

```java title="ScopeGlobal.java"
public class ScopeGlobal {
    static int counter = 0;

    static void increment() {
        counter += 1;   // no local declaration, so this changes the static field
    }

    public static void main(String[] args) {
        increment();
        increment();
        System.out.println(counter);
    }
}
```

</Tab>
<Tab label="C">

```c title="scope_global.c"
#include <stdio.h>

int counter = 0;

void increment(void) {
    counter += 1;   /* no local declaration, so this changes the global */
}

int main(void) {
    increment();
    increment();
    printf("%d\n", counter);
    return 0;
}
```

</Tab>
</Tabs>

All four print:

```text
2
```

Even when a language allows it, modifying globals from inside functions makes code hard to follow, because any function might change them at any time. Prefer passing values in as arguments and returning results.

## Lifetime: when a variable exists

**Scope** is about *where in the source code* a name can be used. **Lifetime** is about *when, while the program runs*, the variable's storage exists.

Usually they line up. A local variable is created when the function is called (its frame is pushed on the call stack) and destroyed when the function returns (the frame is popped). Two calls to the same function get two separate sets of locals, which is also what makes [recursion](../recursion/) work.

They can come apart. A global variable lives for the whole program. And a variable can outlive its function's execution if something still refers to it, as in the next section.

## Closures (a first look)

A function defined inside another can use the outer function's variables. When the inner function is returned or stored, it takes those variables with it. That bundle, a function plus the variables it captured, is a **closure**. Each program below makes two independent counters, calls the first three times and the second once.

<Tabs>
<Tab label="Python">

```python title="closure.py"
def make_counter():
    count = 0

    def next_value():
        nonlocal count
        count += 1
        return count

    return next_value


a = make_counter()
b = make_counter()
print(a(), a(), a())  # 1 2 3
print(b())            # 1: each counter has its own count
```

</Tab>
<Tab label="JavaScript">

```javascript title="closure.js"
function makeCounter() {
  let count = 0;
  return function () {
    count += 1;
    return count;
  };
}

const a = makeCounter();
const b = makeCounter();
console.log(a(), a(), a()); // 1 2 3
console.log(b());           // 1: each counter has its own count
```

</Tab>
<Tab label="Java">

```java title="Closure.java"
import java.util.function.IntSupplier;

public class Closure {
    static IntSupplier makeCounter() {
        int[] count = {0};   // a one-slot array, because a lambda cannot change a plain local
        return () -> {
            count[0] += 1;
            return count[0];
        };
    }

    public static void main(String[] args) {
        IntSupplier a = makeCounter();
        IntSupplier b = makeCounter();
        System.out.println(a.getAsInt() + " " + a.getAsInt() + " " + a.getAsInt());
        System.out.println(b.getAsInt());
    }
}
```

Java lambdas can capture only variables that never change after being set, so the changing count lives inside a small array that the lambda holds on to.

</Tab>
<Tab label="C">

```c title="closure.c"
#include <stdio.h>

typedef struct {
    int count;
} Counter;

int next_value(Counter *counter) {
    counter->count += 1;
    return counter->count;
}

int main(void) {
    Counter a = {0};
    Counter b = {0};
    int first = next_value(&a);
    int second = next_value(&a);
    int third = next_value(&a);
    printf("%d %d %d\n", first, second, third);
    printf("%d\n", next_value(&b));
    return 0;
}
```

C has no closures. The same effect is achieved by keeping the state in a struct and passing it to the function explicitly every time. (The calls are made in separate statements because C does not promise in what order the arguments of one `printf` are evaluated.)

</Tab>
</Tabs>

All four print:

```text
1 2 3
1
```

In the languages with closures, `count` is local to `make_counter`, and `make_counter` has long since returned, yet `a` still increments it. The captured variable lives as long as some function can still reach it, so scope and lifetime are not the same thing. Each call to `make_counter` creates a fresh `count`, which is why `b` starts from 1. (Python's `nonlocal` plays the role for the enclosing function that `global` plays for the top level.)

## Common pitfalls

- **Assuming an assignment inside a function changes the outer variable.** In Python it creates a new local one (shadowing).
- **Using a variable outside the block that created it,** in a language with block scope.
- **Using a variable before it is set.** Python raises `UnboundLocalError`; C silently reads garbage from uninitialised locals.
- **Reusing a loop variable name** like `i` in a nested loop and clobbering the outer one.
- **Relying on globals** for communication between functions.
- **Assuming a local still exists after the call.** Returning a pointer to a local in C is a classic bug, since the frame is gone.

|---|---|---|---|---|

| 2 | `1` | `1` | `1` | `1` |
| 3 | `2` | `2` | `2` | `2` |
| 4 | `NameError` | `ReferenceError` | does not compile | does not compile |

1. The function assigns to `x`, which creates a local (in Python, JavaScript, Java and C alike). The global is untouched, so `x` prints 1.

5. Python has no block scope: after the loop, `i` still exists and holds its last value, 2. In JavaScript `let` confines `i` to the loop, so `typeof` reports `undefined`. Java and C reject the use.
6. `inner` looks up `name`, finds none locally, and checks the enclosing function next, where it finds `"b"`, before it would reach the global `"a"`.

## Summary

- Scope decides where a name can be used: local to a function, global to the file, or (in most languages) local to a block.
- A name is looked up from the innermost scope outward; an inner variable with the same name shadows the outer one without changing it.
- Lifetime is about when the variable exists; usually it ends with its scope, but a closure can keep a variable alive longer.
- Keep scopes small, pass data through parameters and return values, and avoid assigning to globals.
