The [debugging habits lesson](../../beginner/debugging-habits/) taught a routine and the first pdb commands: `breakpoint()`, then `p`, `n`, `s`, `c`, `l`, `w` and `q`. That is enough when you know which line to stop on. This lesson covers what you need when you do not: stopping only in the interesting iteration, inspecting a crash after it happened, and looking inside a program that is already running.

To keep the sessions below reproducible, many of them are driven by a script that feeds pdb its commands as text and captures the output. At your keyboard you type the same commands one at a time after the `(Pdb)` prompt. The scripts print the session without the folder names.

## Breakpoints you set from inside pdb

You do not have to edit the file to stop somewhere. At the prompt, `break` (or `b`) sets a breakpoint at a line number or function name, and `continue` runs until the next one. Here is the tax function from the beginner lesson, driven by a script:

```python title="c39_scripted_pdb.py"
"""Drive pdb from a list of commands, so the session can be checked automatically.

At the keyboard you would type the commands yourself. Here they are fed in as a
string and the output is captured, with the folder name removed.
"""

import io
import os
import pdb


def total_with_tax(prices, rate):
    total = 0
    for price in prices:
        total += price
    return total * 1 + rate


commands = """\
break 16
continue
p total
p rate
p total * 1 + rate
p total * (1 + rate)
continue
"""

out = io.StringIO()
debugger = pdb.Pdb(stdin=io.StringIO(commands), stdout=out)
result = debugger.runcall(total_with_tax, [10, 20], 0.1)

text = out.getvalue().replace(os.getcwd() + os.sep, "")
print(text)
print("returned", result)
```

```text
> c39_scripted_pdb.py(13)total_with_tax()
-> total = 0
(Pdb) Breakpoint 1 at c39_scripted_pdb.py:16
(Pdb) > c39_scripted_pdb.py(16)total_with_tax()
-> return total * 1 + rate
(Pdb) 30
(Pdb) 0.1
(Pdb) 30.1
(Pdb) 33.0
(Pdb) 
returned 30.1
```

`runcall` starts the function under the debugger, which stops on its first line. `break 16` sets a breakpoint on the `return`, and `continue` runs the loop at full speed and stops there. Then four `p` commands inspect the values, including the two competing expressions: `total * 1 + rate` gives the wrong 30.1 and `total * (1 + rate)` gives 33.0. The last `continue` lets the function finish. The `(Pdb)` prompts are all on one line each because the commands were not typed, so the echo of your input is missing.

Useful companions of `break`:

| Command | Effect |
|---|---|
| `break` | List all breakpoints, with hit counts |
| `break 20` / `break module.py:20` / `break function` | Set a breakpoint at a line or function |
| `break 20, i == 3` | Set a **conditional** breakpoint: stop only when the expression is true |
| `tbreak 20` | A temporary breakpoint, removed after the first hit |
| `disable 1` / `enable 1` / `clear 1` | Turn breakpoint 1 off, back on, or delete it |
| `until` / `unt 25` | Run until the line number is greater than the current one, or until line 25: leaves a loop |
| `return` | Run until the current function is about to return |

## Stop only when it matters: conditional breakpoints

A loop with ten thousand iterations is hopeless with `n` and `c` alone. Give the breakpoint a condition and pdb stops only when it holds. `display` is the other time saver: it prints an expression every time execution stops in that frame, and notes when the value has changed.

```python title="c39_ex_cond.py"
import io
import os
import pdb


def running_total(numbers):
    total = 0
    for i, n in enumerate(numbers):
        total += n
    return total


commands = """\
break 9, i == 3
continue
p i, n, total
display total
next
next
continue
"""

out = io.StringIO()
debugger = pdb.Pdb(stdin=io.StringIO(commands), stdout=out)
result = debugger.runcall(running_total, [5, 10, 15, 20, 25])

print(out.getvalue().replace(os.getcwd() + os.sep, ""))
print("returned", result)
```

```text
> c39_ex_cond.py(7)running_total()
-> total = 0
(Pdb) Breakpoint 1 at c39_ex_cond.py:9
(Pdb) > c39_ex_cond.py(9)running_total()
-> total += n
(Pdb) (3, 20, 30)
(Pdb) display total: 30
(Pdb) > c39_ex_cond.py(8)running_total()
-> for i, n in enumerate(numbers):
display total: 50  [old: 30]
(Pdb) > c39_ex_cond.py(9)running_total()
-> total += n
(Pdb) 
returned 75
```

The breakpoint on line 9 has the condition `i == 3`, so pdb skipped the first three iterations. At the stop, `p i, n, total` printed the tuple `(3, 20, 30)`. After `display total`, the next `next` moved to the `for` line and pdb reported that `total` changed from 30 to 50 (the line had run). The final `continue` finished the function with 75.

## Post-mortem: inspect a crash after it happened

When a program has already crashed, you do not need to guess a breakpoint and reproduce it. **Post-mortem debugging** opens the debugger at the point where the exception was raised, with every frame's variables still alive. Run the script under pdb:

```console
$ python -m pdb crash.py
```

If the script ends with an uncaught exception, pdb prints the traceback and drops into a `(Pdb)` prompt inside the failing frame. In an interactive session, `import pdb; pdb.pm()` does the same for the last exception. In code, `pdb.post_mortem()` called in an `except` block does it too. The script below lets pdb post-mortem a caught `KeyError`, feeding it commands so we can read the result:

```python title="c39_postmortem.py"
"""Inspect a crash after the fact, with a scripted post-mortem session."""

import io
import os
import pdb
import sys


def average_by_group(rows):
    sums = {}
    for group, value in rows:
        sums[group] = sums[group] + value
    return sums


rows = [("a", 1), ("b", 2)]
try:
    average_by_group(rows)
except KeyError:
    traceback = sys.exc_info()[2]

commands = """\
where
p group
p value
p sums
up
p rows
quit
"""

out = io.StringIO()
debugger = pdb.Pdb(stdin=io.StringIO(commands), stdout=out)
debugger.reset()
debugger.interaction(None, traceback)

print(out.getvalue().replace(os.getcwd() + os.sep, ""))
```

```text
> c39_postmortem.py(12)average_by_group()
-> sums[group] = sums[group] + value
(Pdb)   c39_postmortem.py(18)<module>()
-> average_by_group(rows)
> c39_postmortem.py(12)average_by_group()
-> sums[group] = sums[group] + value
(Pdb) 'a'
(Pdb) 1
(Pdb) {}
(Pdb) > c39_postmortem.py(18)<module>()
-> average_by_group(rows)
(Pdb) [('a', 1), ('b', 2)]
(Pdb)
```

(`interaction` is the lower-level call that `post_mortem` wraps. You will normally use `pdb.post_mortem()` or `python -m pdb`.) The session lands on line 12 and the bug is plain once you can look: `group` is `'a'`, and `sums` is empty. The code reads `sums[group]` before anything was stored, which raises the `KeyError`. `where` (also `w`) lists the stack of calls with an arrow at the current frame, `up` moves to the caller's frame so you can look at *its* variables (`rows`), and `down` moves back. This is the same chain of frames as the lines in a traceback.

## Turning breakpoint() on and off

`breakpoint()` calls `sys.breakpointhook()`, which by default starts pdb. The environment variable `PYTHONBREAKPOINT` changes what it does, without touching the source. Setting it to `0` disables every `breakpoint()` call. Setting it to the dotted name of a callable runs that instead:

```python title="c39_breakpoint_off.py"
"""breakpoint() calls sys.breakpointhook(), which PYTHONBREAKPOINT can redirect or disable."""

import os
import subprocess
import sys

child_code = """
x = 41
breakpoint()
print("finished without stopping:", x + 1)
"""

env = dict(os.environ, PYTHONBREAKPOINT="0")
result = subprocess.run(
    [sys.executable, "-B", "-c", child_code],
    env=env,
    capture_output=True,
    text=True,
    stdin=subprocess.DEVNULL,
)
print(result.stdout, end="")

# Any importable callable can take over, for example a function that only prints.
env["PYTHONBREAKPOINT"] = "builtins.print"
result = subprocess.run(
    [sys.executable, "-B", "-c", child_code],
    env=env,
    capture_output=True,
    text=True,
    stdin=subprocess.DEVNULL,
)
print(repr(result.stdout))
```

```text
finished without stopping: 42
'\nfinished without stopping: 42\n'
```

With `PYTHONBREAKPOINT=0` the program ran straight through. With `builtins.print`, the `breakpoint()` call became `print()`, which printed an empty line first. In real use, the value might be `pdb.set_trace` (the default) or the name of a different debugger's entry function. The standard library documents `breakpoint()` as available since 3.7, per the [pdb documentation](https://docs.python.org/3/library/pdb.html). Run a test suite or a deployed service with `PYTHONBREAKPOINT=0` and a forgotten `breakpoint()` cannot freeze it.

## Attaching to a running process <Since v="3.14" />

Sometimes the problem is in a program that is already running: a server that has hung, a job that has been going for an hour. You cannot add a `breakpoint()` and restart without losing the state you want to look at. Since Python 3.14, pdb can attach to a running Python process by its process ID (PEP 768):

```console
$ python -m pdb -p 1234
```

The `-p` (or `--pid`) option takes the PID of a process running Python 3.14 or newer. The [pdb documentation](https://docs.python.org/3/library/pdb.html) lists it as "Added in version 3.14". Here is a long-running script to try it on. Start it in one terminal and note the PID that it prints:

```python
import os
import time


def work(n):
    total = 0
    for i in range(n):
        total += i
        time.sleep(0.2)
    return total


print("pid", os.getpid(), flush=True)
print(work(200))
```

In a second terminal, attach with the PID. The commands you type are the usual ones. This session was recorded against the script above with the PID it printed:

```console
$ python -m pdb -p 18660
> /home/you/work.py(9)work()
-> time.sleep(0.2)
(Pdb) where
  /home/you/work.py(14)<module>()
-> print(work(200))
> /home/you/work.py(9)work()
-> time.sleep(0.2)
(Pdb) p i
41
(Pdb) p total
861
(Pdb) quit
```

pdb stopped the program at whatever line it was executing, showed its stack, and let us read `i` and `total` from the live process. Typing `quit` ended the debugging session. The documentation gives one caveat: attaching to a process that is blocked in a system call or waiting for I/O only works once the next bytecode instruction runs, or when the process receives a signal. A script sleeping in `time.sleep` took a moment to respond for that reason. Attaching also needs operating-system permission to inspect the target process, so it works on your own processes and may be refused for others'.

Inside a server you cannot easily attach to, `faulthandler` (to dump the stack of every thread on a signal) is another standard tool to know. Reach for it when you want a stack trace and do not need to step.

## Common pitfalls

- **Leaving `breakpoint()` in code.** A forgotten call freezes a program with nobody at the keyboard. Search for it before committing, as the one-command check in the [test-driven workflow lesson](../test-driven-workflow/) does, or run with `PYTHONBREAKPOINT=0`.
- **A variable named like a pdb command.** `n`, `c`, `l` and `p` are commands. Use `p n` or `!n` to see your variable.
- **Stepping with `n` through a long loop.** Use `until`, a conditional `break`, or `tbreak` instead.
- **Debugging in a test run with output capture.** pytest captures output, which hides the pdb prompt. Use `pytest --pdb` to drop into post-mortem on a failing test, or `pytest -s` to turn capture off.
- **Changing code while stopped.** Edits to the file do not affect the running process. Quit, edit and run again.
- **Attaching to the wrong process.** Check the PID. A shell command like `pgrep -f server.py` helps, and the attach needs Python 3.14 or newer in the *target*, not only in your terminal.

<Exercise title="Find four bugs with pdb">

This inventory report runs without any error, and all four numbers it prints are wrong. The data is `apple,3,0.5`, `pear,12,0.25`, `fig,5,2.0`, `plum,20,0.1`. The correct output is: total value `16.5`, most valuable item `fig` (by quantity times price), low stock (5 or fewer) `['apple', 'fig']`, and names `apple, fig, pear, plum`. Use `breakpoint()` or `python -m pdb` to inspect each function, find the bug in each, and fix it.

```python title="c39_ex_stock.py"
LINES = ["apple,3,0.5", "pear,12,0.25", "fig,5,2.0", "plum,20,0.1"]


def parse_line(line):
    name, qty, price = line.split(",")
    return name, int(qty), float(price)


def total_value(items):
    total = 0
    for name, qty, price in items:
        total = qty * price
    return total


def most_valuable(items):
    best = None
    for item in items:
        if best is None or item[1] * item[2] < best[1] * best[2]:
            best = item
    return best[0]


def low_stock(items, limit=5):
    return [name for name, qty, price in items if qty < limit]


def name_list(items):
    names = sorted(name for name, qty, price in items)
    return ", ".join(names[:-1])


items = [parse_line(line) for line in LINES]
print("total value:", total_value(items))
print("most valuable:", most_valuable(items))
print("low stock:", low_stock(items))
print("names:", name_list(items))
```

```text
total value: 2.0
most valuable: apple
low stock: ['apple']
names: apple, fig, pear
```

<Solution>

Stopping inside each function and printing the values shows:

1. `total_value`: after the loop, `p total` prints `2.0`, the value of the last item alone. The line `total = qty * price` replaces the total on every pass. It should be `total += qty * price`.
2. `most_valuable`: the comparison picks the item with the *smallest* value. `p item[1] * item[2]` and `p best[1] * best[2]` show the order is reversed. Use `>`.
3. `low_stock`: the requirement says 5 or fewer, and `fig` has exactly 5. Use `qty <= limit`.
4. `name_list`: `p names[:-1]` shows the slice drops the last name. Join `names`.

```python title="c39_ex_stock_fixed.py"
LINES = ["apple,3,0.5", "pear,12,0.25", "fig,5,2.0", "plum,20,0.1"]


def parse_line(line):
    name, qty, price = line.split(",")
    return name, int(qty), float(price)


def total_value(items):
    total = 0
    for name, qty, price in items:
        total += qty * price
    return total


def most_valuable(items):
    best = None
    for item in items:
        if best is None or item[1] * item[2] > best[1] * best[2]:
            best = item
    return best[0]


def low_stock(items, limit=5):
    return [name for name, qty, price in items if qty <= limit]


def name_list(items):
    names = sorted(name for name, qty, price in items)
    return ", ".join(names)


items = [parse_line(line) for line in LINES]
print("total value:", total_value(items))
print("most valuable:", most_valuable(items))
print("low stock:", low_stock(items))
print("names:", name_list(items))
```

```text
total value: 16.5
most valuable: fig
low stock: ['apple', 'fig']
names: apple, fig, pear, plum
```

Notice how each bug is a different kind of mistake: the wrong operator, the wrong comparison, an off-by-one at a boundary, and a slice that is too short. Boundary values like `fig` with exactly 5 are the ones a test should include, as in the [test-driven workflow lesson](../test-driven-workflow/).

## Summary

- Set breakpoints from the prompt with `break`, make them conditional with `break 9, i == 3`, and use `tbreak`, `until`, `return` and `display` to avoid stepping line by line.
- After a crash, `python -m pdb script.py`, `pdb.pm()` or `pdb.post_mortem()` opens the debugger inside the failing frame. Use `where`, `up` and `down` to look around.
- `PYTHONBREAKPOINT=0` disables every `breakpoint()` call without editing code.
- `python -m pdb -p PID` <Since v="3.14" /> attaches to a running Python 3.14+ process so you can inspect it without restarting.
