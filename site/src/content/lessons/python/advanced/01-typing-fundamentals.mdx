You already annotate parameters with `int`, `list[str]` and `X | None`, from the [type hints lesson](../../beginner/type-hints-intro/), and you have run a checker in [Linting, formatting and type checking](../../intermediate/ruff-and-type-checking/). This module goes further: it is about making the checker understand real code, not toy functions. The general idea of static versus dynamic typing is in the [fundamentals lesson on values and types](../../../fundamentals/beginner/values-and-types/).

Every checker run in this module was done in October 2026 with mypy 2.3.1 or pyright 1.1.414, targeting Python 3.15, and each output block names the version it came from. Other versions word their messages a little differently. pyright prints absolute file paths; they are shortened here to the file name.

## Ask the checker what it sees

`reveal_type(expr)` asks a type checker to print the type it has inferred. It is the single most useful debugging tool in typing. It lives in `typing` from Python 3.11, and checkers understand it even without the import.

```python title="reveal.py"
from typing import reveal_type

scores = [90, 72, 85]
best = max(scores)
reveal_type(scores)
reveal_type(best)
print(best)
```

```text
90
```

At run time, `reveal_type` returns its argument unchanged and writes a line such as `Runtime type is 'list'` to standard error, which is why only `90` appears above. The checker reports something more useful:

```console title="mypy 2.3.1"
$ mypy reveal.py
reveal.py:5: note: Revealed type is "list[int]"
reveal.py:6: note: Revealed type is "int"
Success: no issues found in 1 source file
```

Delete `reveal_type` calls once you have your answer. They are questions, not documentation.

## Functions as values: Callable

A parameter that receives a function is annotated with `Callable[[arg types], return type]`. Import it from `collections.abc`, which is the current home; `typing.Callable` is an older alias.

```python title="callable_apply.py"
from collections.abc import Callable


def apply_twice(func: Callable[[int], int], value: int) -> int:
    return func(func(value))


def add_three(n: int) -> int:
    return n + 3


print(apply_twice(add_three, 10))
print(apply_twice(lambda n: n * n, 3))
```

```text
16
81
```

The lambda needs no annotation of its own. The checker sees that it is passed where a `Callable[[int], int]` is expected and checks `n * n` with `n: int`.

Now pass a function with the wrong return type. Python is happy, because `"#1"` can be formatted again:

```python title="callable_wrong.py"
from collections.abc import Callable


def apply_twice(func: Callable[[int], int], value: int) -> int:
    return func(func(value))


def label(n: int) -> str:
    return f"#{n}"


print(apply_twice(label, 1))
```

```text
##1
```

The output `##1` is the kind of quiet nonsense that reaches production. The checker refuses it:

```console title="mypy 2.3.1"
$ mypy callable_wrong.py
callable_wrong.py:12: error: Argument 1 to "apply_twice" has incompatible type "Callable[[int], str]"; expected "Callable[[int], int]"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

`Callable` describes positional parameters only. Keyword arguments, defaults and overloads need a callable protocol, which is in [Protocols and structural typing](../protocols-structural/).

## A fixed set of values: Literal

`Literal["left", "right", "center"]` is a type with exactly three values. It documents an option parameter more precisely than `str`, and a checker rejects anything else. Assigning it to a name makes a reusable alias.

```python title="literal_align.py"
from typing import Literal, get_args

Align = Literal["left", "right", "center"]


def pad(text: str, width: int, align: Align = "left") -> str:
    if align == "left":
        return text.ljust(width)
    if align == "right":
        return text.rjust(width)
    return text.center(width)


print(f"[{pad('ok', 6)}]")
print(f"[{pad('ok', 6, 'right')}]")
print(f"[{pad('ok', 6, 'middle')}]")
print(get_args(Align))
```

```text
[ok    ]
[    ok]
[  ok  ]
('left', 'right', 'center')
```

At run time `'middle'` fell through to the last branch and nobody noticed. `get_args` shows that the allowed values are stored on the alias, which libraries use to build command-line choices or validation. The checker catches the typo:

```console title="mypy 2.3.1"
$ mypy literal_align.py
literal_align.py:16: error: Argument 3 to "pad" has incompatible type "Literal['middle']"; expected "Literal['left', 'right', 'center']"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

Literal values can be strings, integers, bytes, `True`, `False`, `None` and enum members. Arbitrary expressions are not allowed.

## Constants: Final

`Final` tells the checker that a name must not be rebound. It is the closest Python has to a constant.

```python title="final_const.py"
from typing import Final

MAX_RETRIES: Final = 3
print(MAX_RETRIES)

MAX_RETRIES = 5
print(MAX_RETRIES)
```

```text
3
5
```

Python rebound the name without complaint. The checker did not:

```console title="mypy 2.3.1"
$ mypy final_const.py
final_const.py:6: error: Cannot assign to final name "MAX_RETRIES"  [misc]
Found 1 error in 1 file (checked 1 source file)
```

`MAX_RETRIES: Final = 3` lets the checker infer `int`. Write `Final[int]` only when you want a wider type than the value suggests. In a class body, `Final` marks an attribute that subclasses and instances may not replace.

## Shared class attributes: ClassVar

An annotation in a class body normally declares an instance attribute. `ClassVar[T]` says the opposite: the value belongs to the class, and instances only read it. Dataclasses act on that at run time, by leaving `ClassVar` names out of the fields:

```python title="classvar_count.py"
from dataclasses import dataclass, fields
from typing import ClassVar


@dataclass
class Connection:
    host: str
    port: int = 5432
    opened: ClassVar[int] = 0

    def __post_init__(self) -> None:
        Connection.opened += 1


a = Connection("db1")
b = Connection("db2", 6543)
print([f.name for f in fields(Connection)], Connection.opened)
a.opened = 99
print(Connection.opened, a.opened)
```

```text
['host', 'port'] 2
2 99
```

`opened` is not a parameter of `__init__`, and the counter is shared. The last two lines show the usual mistake: `a.opened = 99` did not change the counter, it created an instance attribute that hides it. The checker reports it:

```console title="mypy 2.3.1"
$ mypy classvar_count.py
classvar_count.py:18: error: Cannot assign to class variable "opened" via instance  [misc]
Found 1 error in 1 file (checked 1 source file)
```

Registries and counters on a base class, like the plugin registry in [Customising classes](../class-customisation/), are class variables, so annotate them with `ClassVar`.

## The shape of a dict: TypedDict

JSON, configuration and many APIs hand you dicts with known keys. `dict[str, object]` loses all that knowledge. A `TypedDict` lists each key and its value type.

```python title="typeddict_basic.py"
from typing import TypedDict


class Movie(TypedDict):
    title: str
    year: int


film: Movie = {"title": "Alien", "year": 1979}
print(film["title"], film["year"])
print(type(film) is dict)
print(sorted(Movie.__required_keys__))
print(Movie(title="Heat", year=1995))
```

```text
Alien 1979
True
['title', 'year']
{'title': 'Heat', 'year': 1995}
```

At run time a `TypedDict` value is an ordinary `dict`. Calling `Movie(...)` builds one, and the class keeps the key names in `__required_keys__`. All the checking is static. A typo is caught twice, once for the key that is missing and once for the stranger:

```python title="typeddict_typo.py"
from typing import TypedDict


class Movie(TypedDict):
    title: str
    year: int


film: Movie = {"title": "Alien", "yaer": 1979}
print(film)
```

```text
{'title': 'Alien', 'yaer': 1979}
```

```console title="mypy 2.3.1"
$ mypy typeddict_typo.py
typeddict_typo.py:9: error: Missing key "year" for TypedDict "Movie"  [typeddict-item]
typeddict_typo.py:9: error: Extra key "yaer" for TypedDict "Movie"  [typeddict-unknown-key]
Found 2 errors in 1 file (checked 1 source file)
```

If you control the data and want behaviour, a dataclass from [Dataclasses](../../intermediate/dataclasses/) is usually better. Reach for `TypedDict` when the value really is a dict, for example straight out of `json.loads`. Optional keys, read-only keys and extra keys are in [TypedDict in depth](../typeddict-advanced/).

## Any versus object

Both accept every value, but they mean opposite things:

- `object` says "anything, so you may only do what every object can do".
- `Any` says "stop checking": every operation is allowed, and the result is `Any` too.

```python title="any_object.py"
from typing import Any


def loose(value: Any) -> int:
    return value.bit_length()


def strict(value: object) -> int:
    return value.bit_length()


print(loose(255), strict(255))
try:
    loose("255")
except AttributeError as error:
    print("AttributeError:", error)
```

```text
8 8
AttributeError: 'str' object has no attribute 'bit_length'
```

```console title="mypy 2.3.1"
$ mypy any_object.py
any_object.py:9: error: "object" has no attribute "bit_length"  [attr-defined]
Found 1 error in 1 file (checked 1 source file)
```

The checker flags `strict`, whose body really is wrong for most inputs, and says nothing about `loose("255")`, which crashed. `Any` spreads: anything computed from an `Any` is `Any`, so one careless annotation can switch checking off for a whole call chain. With `object` you must prove the type first, and an `isinstance` check does that:

```python title="object_narrowed.py"
def strict(value: object) -> int:
    if isinstance(value, int):
        return value.bit_length()
    return 0


print(strict(255), strict("255"))
```

```text
8 0
```

```console title="mypy 2.3.1"
$ mypy object_narrowed.py
Success: no issues found in 1 source file
```

Use `object` for "I accept anything and only pass it along or inspect it". Keep `Any` for the boundary with untyped code, and for the rare value whose type you genuinely cannot express.

## Overriding the checker: cast

`cast(T, value)` tells the checker "treat this as `T`". At run time it returns `value` untouched, with no conversion and no check.

```python title="cast_json.py"
import json
from typing import TypedDict, cast


class Item(TypedDict):
    sku: str
    qty: int


item = cast(Item, json.loads('{"sku": "A1", "qty": 4}'))
print(item["sku"], item["qty"] * 2)

wrong = cast(int, "not a number")
print(repr(wrong), type(wrong).__name__)
```

```text
A1 8
'not a number' str
```

`json.loads` returns `Any`, so the cast to `Item` lets the rest of the code use precise key types. The second cast shows the danger: the checker now believes `wrong` is an `int`, and nothing at run time disagrees until something breaks far away. Every `cast` is an unchecked claim, so keep them few, close to the source of the data, and preferably replaced by a real check or by narrowing, which [Type narrowing](../narrowing/) covers.

## Distinct types for the same value: NewType

User IDs and order IDs are both `int`, and passing one where the other belongs is a classic bug. `NewType("UserId", int)` creates a type that the checker treats as a separate subtype of `int`. At run time it costs nothing: calling `UserId(42)` returns `42` unchanged.

```python title="newtype_ids.py"
from typing import NewType

UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)


def cancel(order: OrderId) -> str:
    return f"cancelled order {order}"


uid = UserId(42)
print(uid, type(uid).__name__, uid + 1)
print(UserId)
print(cancel(OrderId(7)))
print(cancel(uid))
```

```text
42 int 43
__main__.UserId
cancelled order 7
cancelled order 42
```

```console title="mypy 2.3.1"
$ mypy newtype_ids.py
newtype_ids.py:15: error: Argument 1 to "cancel" has incompatible type "UserId"; expected "OrderId"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

The value is a plain `int`, so arithmetic works and gives an `int`. Only the checker keeps the two kinds of ID apart. A `NewType` is not a class: you cannot subclass it or use it with `isinstance`. When you need run-time behaviour, write a real class.

## When not to type more precisely

Precision has a cost in reading time. A `Literal` alias for three option strings pays for itself; a `NewType` for every integer in a program does not. Add a precise type where a mix-up is likely and expensive, such as IDs, units or option names, and where the checker can then catch it. Leave short scripts, notebooks and throwaway code with plain annotations or none. And do not type around a design problem: if a function needs several casts and a page of annotations to describe, a simpler signature is usually the better fix.

## Common pitfalls

**Reading hints as runtime checks.** Every example above ran past its type error. Annotations are enforced only by a checker, or by a library you choose to use, such as a validator.

**Typing parameters too narrowly.** A function that only iterates should accept `Iterable[str]` from `collections.abc`, not `list[str]`. Accept the most general type you need and return the most specific type you have.

**Silencing with Any.** Writing `Any` to make an error go away turns off the very check that found the problem. Find the type the code really needs, or use `object` and narrow.

**Expecting Final to freeze the value.** `Final` stops rebinding the name. A `Final` list can still be appended to.

<Exercise title="A typed dispatch table">
Write `OPERATIONS`, a dict from the operation names `"add"`, `"sub"` and `"mul"` to two-argument integer functions, and `calc(op, a, b)` that looks up and calls one. Use a `Literal` alias for the names, so that `calc("div", 6, 3)` is a checker error. Loop over the alias's values with `get_args` and print each result for `6` and `3`.

Expected output, and `Success` from mypy:

```text
add 9
sub 3
mul 18
```

<Solution>

```python title="dispatch.py"
from collections.abc import Callable
from typing import Literal, get_args

Op = Literal["add", "sub", "mul"]

OPERATIONS: dict[Op, Callable[[int, int], int]] = {
    "add": lambda a, b: a + b,
    "sub": lambda a, b: a - b,
    "mul": lambda a, b: a * b,
}


def calc(op: Op, a: int, b: int) -> int:
    return OPERATIONS[op](a, b)


NAMES: tuple[Op, ...] = get_args(Op)
for name in NAMES:
    print(name, calc(name, 6, 3))
```

```text
add 9
sub 3
mul 18
```

```console title="mypy 2.3.1"
$ mypy dispatch.py
Success: no issues found in 1 source file
```

`get_args` returns `tuple[Any, ...]`, so looping over it directly would make `name` an `Any`, and `calc(name, ...)` would pass for the wrong reason. Annotating `NAMES` states once that the tuple holds `Op` values, and every call after that is checked.

With the alias in place, a bad name is caught before the program runs. At run time it would have been a `KeyError`:

}

## Summary

- `reveal_type(expr)` shows what the checker inferred. Remove it when you are done.
- `Callable[[int], int]` from `collections.abc` types a function argument by its positional parameters and return type.
- `Literal[...]` restricts a value to a fixed set, and `get_args` reads that set at run time.
- `Final` forbids rebinding a name, but does not freeze the object. `ClassVar` marks an attribute that belongs to the class, and dataclasses leave it out of the fields.
- `TypedDict` describes dict shapes for checkers. At run time the values are plain dicts.
- `object` accepts everything and allows little. `Any` accepts everything and checks nothing.
- `cast` changes only what the checker believes. Use it sparingly, at data boundaries.
- `NewType` gives one run-time type, such as `int`, several names that the checker keeps apart.
