This lesson has no new topics. You will build one tool from the four advanced modules: typing, data handling, concurrency and metaprogramming. Each step ends with a result you can check before you move on. When a piece feels shaky, the step that uses it links back to its lesson.

The tool is **jobrun**, a small job runner. It reads a JSON file that lists jobs, runs all of them at once, and prints one line per job. Each kind of job is a *plugin*: a class that registers itself just by being defined. Some jobs wait on (simulated) network calls, so they suit `asyncio`. One does real CPU work, so it runs in a worker pool. Every job has a deadline, and a job that fails or runs late is reported without stopping the others.

## The specification

- `jobrun JOBS.json` runs every job in the file at the same time and prints one line per job, in file order, followed by a summary.
- A job's line says `ok`, `failed` or `timeout`, with a result or a reason.
- The exit code is 0 when every job is `ok`, 1 when any job failed or timed out, and 2 when the file itself is unusable.
- A new kind of job is a new class. Nothing else in the program changes.
- `--pool interpreter` runs CPU work in subinterpreters instead of processes.
- The package passes `mypy --strict`, and the code is covered by automated tests.

The jobs file names a deadline for each job (`timeout`, in seconds), the number of pool workers, and the jobs. Each job has an `id`, a `kind`, and whatever settings its kind needs:

```json title="jobs.json"
{
  "timeout": 0.5,
  "workers": 2,
  "jobs": [
    {"id": "motto", "kind": "words",
     "text": "Simple is better than complex. Complex is better than complicated."},
    {"id": "server-log", "kind": "levels",
     "log": "09:00:01 INFO start\n09:00:02 WARN disk 91%\n09:00:05 ERROR disk full\nnot a log line\n09:00:09 INFO retry"},
    {"id": "primes", "kind": "primes", "below": 30000},
    {"id": "primes-bad", "kind": "primes", "below": 1},
    {"id": "quick-api", "kind": "wait", "seconds": 0.1},
    {"id": "slow-api", "kind": "wait", "seconds": 5}
  ]
}
```

Two of the jobs are meant to go wrong: `primes-bad` asks for an impossible count, and `slow-api` takes ten times longer than the deadline allows. The finished program must report both and still finish the other four, in about half a second in total.

## Step 1: the shared types

Start with the vocabulary every other module uses. A job ends with an `Outcome`: which job, a `Status`, and a line of detail. A `Context` carries what a running job may use, which for now is a worker pool. A `Sink` is anything the report can be written to.

```python title="src/jobrun/models.py"
from concurrent.futures import Executor
from dataclasses import dataclass
from enum import StrEnum
from typing import Protocol


class ConfigError(ValueError):
    """The jobs file does not have the expected shape."""


class Status(StrEnum):
    OK = "ok"
    FAILED = "failed"
    TIMEOUT = "timeout"


@dataclass(frozen=True)
class Outcome:
    job_id: str
    status: Status
    detail: str
```

`Context.pool` is typed as `concurrent.futures.Executor`, the base class of every pool, so a process pool, an interpreter pool and a thread pool all fit. `Sink` is a [protocol](../protocols-structural/): any object with a matching `write` method satisfies it, without inheriting from anything. The `/` makes `text` positional-only, which matches how `sys.stdout.write` is declared, and the return type `object` accepts methods that return a count (as `TextIO.write` does) or nothing.

```python title="src/jobrun/models.py (continued)"
@dataclass(frozen=True)
class Context:
    """What every job may use while it runs."""

    pool: Executor


class Sink(Protocol):
    """Anything with a write(str) method: sys.stdout, io.StringIO, a file."""

    def write(self, text: str, /) -> object: ...
```

## Step 2: a plugin base class that registers its subclasses

Every kind of job will be a subclass of one generic base class, `Plugin[T]`. The type parameter `T` is the type of value the job's `run` produces, and `render` must accept exactly that type. The checker can then prove that each plugin's two halves fit together, which step 7 shows.

Registration uses [`__init_subclass__`](../class-customisation/). Python calls it on the base class whenever a subclass is created, and passes it the keyword arguments from the `class` line. So `class WordCount(Plugin[...], kind="words")` is enough to add `"words"` to the registry.

```python title="src/jobrun/plugin.py"
from dataclasses import dataclass
from typing import Any, ClassVar, Self

from .models import Context


@dataclass(frozen=True)
class Plugin[T]:
    """One job. T is the type of the value that run() produces."""

    kind: ClassVar[str]
    job_id: str

    def __init_subclass__(cls, /, kind: str, **kwargs: Any) -> None:
        super().__init_subclass__(**kwargs)
        if kind in REGISTRY:
            raise TypeError(f"plugin kind {kind!r} is already registered")
        cls.kind = kind
        REGISTRY[kind] = cls
```

The base class also defines the three methods every plugin provides. `from_params` is a class method that builds a plugin from the settings in the jobs file and returns `Self`, so `WordCount.from_params` is known to return a `WordCount`. `kind` is a `ClassVar`, so the dataclass leaves it out of the fields.

```python title="src/jobrun/plugin.py (continued)"
    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        raise NotImplementedError

    async def run(self, ctx: Context) -> T:
        raise NotImplementedError

    def render(self, value: T) -> str:
        return str(value)


# Defined after the class, because its annotation names the class. Subclasses
# are created later, so __init_subclass__ always finds it.
REGISTRY: dict[str, type[Plugin[Any]]] = {}
```

The comment on `REGISTRY` matters for 3.12 and 3.13, which evaluate module-level annotations at once. There, `type[Plugin[Any]]` above the class would be a `NameError`. Try the registry with a throwaway plugin:

```python title="try_registry.py"

        return cls(job_id, str(params["text"]))

    def render(self, value: str) -> str:
        return value.upper() + "!"


print(REGISTRY)

```

## Step 3: four plugins

`builtin.py` holds the plugins that ship with the tool. Each one is a frozen dataclass that names its result type in the `class` line, and each `from_params` uses [`match`](../match-advanced/) to check the settings and pull them out in one move. A mapping pattern ignores keys it does not mention, so the `id` and `kind` keys that are still in the settings do no harm.

```python title="src/jobrun/builtin.py"
import asyncio
import re
from collections import Counter
from dataclasses import dataclass
from math import isqrt
from typing import Self

from .models import ConfigError, Context
from .plugin import Plugin

WORD = re.compile(r"[a-z']+")
LOG_LINE = re.compile(r"(?P<time>[\d:]{8}) (?P<level>[A-Z]+) (?P<text>.*)")
```

The first plugin counts words with a [regex](../regex/) and a [`Counter`](../collections-module/). Its `run` does not await anything, which is allowed: an `async def` that never pauses still fits the same interface.

```python title="src/jobrun/builtin.py (continued)"
@dataclass(frozen=True)
class WordCount(Plugin[list[tuple[str, int]]], kind="words"):
    """The three most common words in a text."""

    text: str

    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        match params:
            case {"text": str(text)}:
                return cls(job_id, text)
            case _:
                raise ConfigError(f"{job_id}: 'words' needs a string 'text'")

    async def run(self, ctx: Context) -> list[tuple[str, int]]:
        return Counter(WORD.findall(self.text.lower())).most_common(3)

    def render(self, value: list[tuple[str, int]]) -> str:
        return ", ".join(f"{word}={count}" for word, count in value)
```

The second counts log lines per level. `fullmatch` returns a match or `None`, and a `match` statement on that result reads like the two cases it is. The named group is read with `found["level"]`.

```python title="src/jobrun/builtin.py (continued)"
@dataclass(frozen=True)
class LogLevels(Plugin[Counter[str]], kind="levels"):
    """Log lines per level. A line that does not parse counts as '?'."""

    log: str

    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        match params:
            case {"log": str(log)}:
                return cls(job_id, log)
            case _:
                raise ConfigError(f"{job_id}: 'levels' needs a string 'log'")
```

```python title="src/jobrun/builtin.py (continued)"
    async def run(self, ctx: Context) -> Counter[str]:
        levels = Counter[str]()
        for line in self.log.splitlines():
            match LOG_LINE.fullmatch(line):
                case None:
                    levels["?"] += 1
                case found:
                    levels[found["level"]] += 1
        return levels

    def render(self, value: Counter[str]) -> str:
        return " ".join(f"{level}={n}" for level, n in value.most_common())
```

The third stands in for a slow network call. It is the job that really awaits, so it is the one a deadline can interrupt. The pattern `int() | float() as seconds` accepts both kinds of JSON number, and the guard rejects negative ones.

```python title="src/jobrun/builtin.py (continued)"
@dataclass(frozen=True)
class Wait(Plugin[float], kind="wait"):
    """A stand-in for a slow network call: it sleeps, then reports."""

    seconds: float

    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        match params:
            case {"seconds": int() | float() as seconds} if seconds >= 0:
                return cls(job_id, float(seconds))
            case _:
                raise ConfigError(f"{job_id}: 'wait' needs 'seconds' >= 0")

    async def run(self, ctx: Context) -> float:
        await asyncio.sleep(self.seconds)
        return self.seconds

    def render(self, value: float) -> str:
        return f"waited {value}s"
```

The fourth does CPU work. Run directly in a coroutine, that work would freeze the event loop and every other job with it ([concurrency models](../concurrency-models/) explained why). So the computation is a plain module-level function, which a [process pool](../multiprocessing/) can find by name in another process.

```python title="src/jobrun/builtin.py (continued)"
def count_primes(below: int) -> int:
    """CPU-bound on purpose. It runs in a worker, never on the event loop."""
    if below < 2:
        raise ValueError(f"below must be at least 2, got {below}")
    count = 0
    for n in range(2, below):
        for d in range(2, isqrt(n) + 1):
            if n % d == 0:
                break
        else:
            count += 1
    return count
```

The plugin hands the function to the pool with `loop.run_in_executor(executor, function, *args)`. This is the general form of the `asyncio.to_thread` from [asyncio fundamentals](../asyncio-basics/): it submits the call to any executor and gives back something to await, so the event loop keeps running the other jobs while a worker computes.

```python title="src/jobrun/builtin.py (continued)"
@dataclass(frozen=True)
class Primes(Plugin[int], kind="primes"):
    """How many primes are below a number, computed in the worker pool."""

    below: int

    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        match params:
            case {"below": int(below)}:
                return cls(job_id, below)
            case _:
                raise ConfigError(f"{job_id}: 'primes' needs an int 'below'")

    async def run(self, ctx: Context) -> int:
        loop = asyncio.get_running_loop()
        return await loop.run_in_executor(ctx.pool, count_primes, self.below)

    def render(self, value: int) -> str:
        return f"{value} primes below {self.below}"
```

## Step 4: reading the jobs file with match

JSON arrives as dictionaries, lists, strings and numbers, with no promises. `config.py` turns it into a frozen `Config` that holds real plugin objects, or raises `ConfigError` with a message that names the problem. The first import matters more than it looks: plugins register when their module is imported, so `config.py` imports `builtin` for that side effect alone.

```python title="step 4, src/jobrun/config.py"
import json
from dataclasses import dataclass
from pathlib import Path
from typing import Any

from . import builtin  # noqa: F401  Importing it registers the plugins.
from .models import ConfigError
from .plugin import REGISTRY, Plugin


@dataclass(frozen=True)
class Config:
    timeout: float
    workers: int
    jobs: tuple[Plugin[Any], ...]


def parse_job(raw: object) -> Plugin[Any]:
    match raw:
        case {"id": str(job_id), "kind": str(kind), **params}:
            if kind not in REGISTRY:
                raise ConfigError(f"{job_id}: unknown kind {kind!r}")
            return REGISTRY[kind].from_params(job_id, params)
        case _:
            raise ConfigError(f"a job needs a string id and kind: {raw!r}")
```

`parse_job` takes `object`, the honest type of something from `json.loads`. One mapping pattern checks that it is a dictionary, that `id` and `kind` are strings, and collects every other key into `params` with `**params`. The registry then picks the class, and the class checks its own settings. `parse_config` does the same for the whole file, with a guard for the two positive numbers:

```python title="step 4, src/jobrun/config.py (continued)"
def parse_config(data: object) -> Config:
    match data:
        case {
            "timeout": int() | float() as timeout,
            "workers": int(workers),
            "jobs": [*raw_jobs],
        } if timeout > 0 and workers > 0:
            jobs = tuple(parse_job(raw) for raw in raw_jobs)
            return Config(float(timeout), workers, jobs)
        case _:
            raise ConfigError(
                "expected positive 'timeout' and 'workers', and a 'jobs' list"
            )


def load_config(path: Path) -> Config:
    try:
        data = json.loads(path.read_text(encoding="utf-8"))
    except json.JSONDecodeError as error:
        raise ConfigError(f"{path} is not valid JSON: {error}") from error
    return parse_config(data)
```

## Step 5: running every job at once

`runner.py` is short, because the earlier steps did the hard work. `execute` runs one job under a deadline and always returns an `Outcome`. It turns every ordinary exception into a `failed` outcome, so one bad job cannot bring down the others. It is a generic function, `execute[T]`, so the checker knows that the value from `job.run` is exactly what `job.render` accepts.

```python title="src/jobrun/runner.py"
import asyncio

from .config import Config
from .models import Context, Outcome, Status
from .plugin import Plugin


async def execute[T](job: Plugin[T], ctx: Context, timeout: float) -> Outcome:
    try:
        async with asyncio.timeout(timeout):
            value = await job.run(ctx)
    except TimeoutError:
        detail = f"no result after {timeout}s"
        return Outcome(job.job_id, Status.TIMEOUT, detail)
    except Exception as error:
        detail = f"{type(error).__name__}: {error}"
        return Outcome(job.job_id, Status.FAILED, detail)
    return Outcome(job.job_id, Status.OK, job.render(value))
```

The `try` sits *outside* the `async with`, as [structured concurrency](../asyncio-structured/) taught: `asyncio.timeout` turns the cancellation into `TimeoutError` only when its block exits. `except Exception` does not catch `CancelledError`, which is a `BaseException`, so cancellation still works.

`run_all` starts one task per job in a `TaskGroup`. Leaving the `async with` block waits for all of them, and the list of tasks keeps the order of the file, whatever order the jobs finish in.

```python title="src/jobrun/runner.py (continued)"
async def run_all(config: Config, ctx: Context) -> list[Outcome]:
    async with asyncio.TaskGroup() as tg:
        tasks = [
            tg.create_task(execute(job, ctx, config.timeout), name=job.job_id)
            for job in config.jobs
        ]
    return [task.result() for task in tasks]
```

Run the real jobs file:

The `motto` line shows a tie: `is`, `better`, `than` and `complex` all appear twice, and `most_common` keeps the first three it met.

## Step 6: the command

`cli.py` adds the pool choice, the report and the exit code. `make_pool` uses `match` on the pool's name. The interpreter branch imports `InterpreterPoolExecutor` only when asked, so the rest of the tool still runs on 3.12 and 3.13.

```python title="src/jobrun/cli.py"
import argparse
import asyncio
import sys
from collections import Counter
from concurrent.futures import Executor, ProcessPoolExecutor
from pathlib import Path

from .config import load_config
from .models import ConfigError, Context, Outcome, Sink, Status
from .runner import run_all


def make_pool(kind: str, workers: int) -> Executor:
    match kind:
        case "process":
            return ProcessPoolExecutor(max_workers=workers)
        case "interpreter":
            from concurrent.futures import InterpreterPoolExecutor

            return InterpreterPoolExecutor(max_workers=workers)
        case _:
            raise ValueError(f"unknown pool kind {kind!r}")
```

`report` writes to a `Sink`, so the tests can pass a `StringIO`. The column width comes from the longest job id, and a `Counter` of statuses gives the summary line, listed in the enum's order and without zero counts.

```python title="src/jobrun/cli.py (continued)"
def report(outcomes: list[Outcome], out: Sink) -> None:
    width = max((len(o.job_id) for o in outcomes), default=0) + 2
    for o in outcomes:
        out.write(f"{o.job_id:<{width}}{o.status:<9}{o.detail}\n")
    counts = Counter(o.status for o in outcomes)
    parts = [f"{counts[s]} {s}" for s in Status if counts[s]]
    out.write(f"{len(outcomes)} jobs: {', '.join(parts)}\n")


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="jobrun")
    parser.add_argument("jobs", type=Path, help="JSON file of jobs")
    parser.add_argument(
        "--pool", choices=["process", "interpreter"], default="process"
    )
    return parser
```

`main` returns the exit code, which the installed `jobrun` script passes to `sys.exit`. The pool is a context manager, so it shuts down even if `run_all` raises.

```python title="src/jobrun/cli.py (continued)"
def main(argv: list[str] | None = None, out: Sink | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        config = load_config(args.jobs)
    except (OSError, ConfigError) as error:
        print(f"jobrun: {error}", file=sys.stderr)
        return 2
    with make_pool(args.pool, config.workers) as pool:
        outcomes = asyncio.run(run_all(config, Context(pool)))
    report(outcomes, out if out is not None else sys.stdout)
    return 0 if all(o.status is Status.OK for o in outcomes) else 1
```

Mypy is right in general. `raw` is any `object`, so a mapping that matches the pattern could have keys of any type, and `**params` is typed `dict[object, object]`. Pyright types `params` as `dict[Unknown, Unknown]`. `Unknown` is its name for a type it could not work out, and in its default mode it does not report one, so a clean pyright run is not proof that a value was [narrowed](../narrowing/). JSON object keys are always strings, so the fix is to say so in code, where both the checker and the reader can see it:

```python title="src/jobrun/config.py (changed: parse_job)"
def parse_job(raw: object) -> Plugin[Any]:
    match raw:
        case {"id": str(job_id), "kind": str(kind), **rest}:
            if kind not in REGISTRY:
                raise ConfigError(f"{job_id}: unknown kind {kind!r}")
            params = {str(key): value for key, value in rest.items()}
            return REGISTRY[kind].from_params(job_id, params)
        case _:
            raise ConfigError(f"a job needs a string id and kind: {raw!r}")
```

## Common pitfalls

- **A plugin module nobody imports.** Registration happens when the `class` statement runs, which is when its module is imported. A plugin in a module that nothing imports does not exist as far as the registry knows. That is why `config.py` imports `builtin`.
- **`@dataclass(slots=True)` on a plugin.** With slots, the decorator builds a *new* class from the old one. Creating that class calls `__init_subclass__` a second time, without the `kind=` keyword, so it fails with the "missing 1 required positional argument: 'kind'" error from step 2. The plugins here leave `slots` off.
- **`True` is an `int`.** `bool` is a subclass of `int`, so the pattern `int(below)` accepts `{"below": true}` and builds `Primes(below=True)`. Add a `case {"below": bool()}` that raises before the `int` case if that matters.
- **CPU work in `run` without the pool.** A loop inside an `async def` holds the event loop until it ends. Every other job, and every deadline, waits. `asyncio.timeout` cannot interrupt code that never reaches an `await`.
- **A deadline does not stop a worker.** When a pooled job times out, the coroutine stops waiting, but the worker process or interpreter keeps computing until the function returns, and the pool's `with` block waits for it at shutdown. Make CPU jobs small, or check a limit inside the function.
- **Missing main guards with pytest run from a script.** <Since v="3.14" /> On Linux, process pools start workers with `forkserver` by default, and workers import the main module again. When a script runs `pytest.main()` at top level, every worker starts the test suite again, and the test that uses the pool fails. Put the call under `if __name__ == "__main__":`.
- **Interpreter workers start fresh.** A subinterpreter builds its own `sys.path` at startup, from the environment and the installed packages. A `sys.path.insert` done at run time in the main interpreter does not reach it, and the import of your module fails there. Install the package (`pip install -e .`) instead.

```python title="ext_grep.py (continued)"
@dataclass(frozen=True)
class Grep(Plugin[list[str]], kind="grep"):
    """The lines of a log that match a regular expression."""

    pattern: re.Pattern[str]
    log: str

    @classmethod
    def from_params(cls, job_id: str, params: dict[str, object]) -> Self:
        match params:
            case {"pattern": str(text), "log": str(log)}:
                try:
                    return cls(job_id, re.compile(text), log)
                except re.error as error:
                    raise ConfigError(f"{job_id}: bad pattern: {error}")
            case _:
                raise ConfigError(f"{job_id}: 'grep' needs 'pattern' and 'log'")

    async def run(self, ctx: Context) -> list[str]:
        lines = self.log.splitlines()
        return [line for line in lines if self.pattern.search(line)]

    def render(self, value: list[str]) -> str:
        return f"{len(value)} found: " + " | ".join(value)
```

<Exercise title="Fail fast">

<Since v="3.15" /> Write `run_fail_fast(config, ctx)`, which stops the whole group as soon as one job does not succeed, using `TaskGroup.cancel()`. Return a `dict` of the outcomes that did arrive, and print `cancelled` for the jobs that are missing from it. The job that fails must still be reported. With a word count, the impossible prime count and a 5-second wait, the program must end at once, not after 5 seconds, and print:

```text
motto: ok
primes-bad: failed
slow-api: cancelled
```

<Solution>

```python title="ext_fail_fast.py"
import asyncio
from concurrent.futures import ThreadPoolExecutor
from typing import Any

from jobrun.config import Config, parse_config
from jobrun.models import Context, Outcome, Status
from jobrun.plugin import Plugin
from jobrun.runner import execute


async def run_fail_fast(config: Config, ctx: Context) -> dict[str, Outcome]:
    finished: dict[str, Outcome] = {}
    async with asyncio.TaskGroup() as tg:

        async def guarded(job: Plugin[Any]) -> None:
            outcome = await execute(job, ctx, config.timeout)
            finished[job.job_id] = outcome
            if outcome.status is not Status.OK:
                tg.cancel()

        for job in config.jobs:
            tg.create_task(guarded(job))
    return finished
```

```python title="ext_fail_fast.py (continued)"
config = parse_config({"timeout": 10, "workers": 1, "jobs": [
    {"id": "motto", "kind": "words", "text": "Now is better than never."},
    {"id": "primes-bad", "kind": "primes", "below": 1},
    {"id": "slow-api", "kind": "wait", "seconds": 5},
]})
with ThreadPoolExecutor() as pool:
    finished = asyncio.run(run_fail_fast(config, Context(pool)))
for job in config.jobs:
    outcome = finished.get(job.job_id)
    print(job.job_id, outcome.status if outcome else "cancelled", sep=": ")
```

```text

primes-bad: failed
slow-api: cancelled
```

The outcome is stored *before* `tg.cancel()`, and that order matters. `cancel()` cancels every task in the group that is not done, including the one that calls it, so a task that returned its outcome after cancelling could lose it. The group then exits normally, with no `CancelledError` to catch. Before 3.15 you would raise a private exception in the task and catch it with `except*` around the group.
