This lesson has no new topics. It takes one program through the whole expert level: measure it, change the slow part, make it observable, package it, and check that it is ready for 3.15 and the free-threaded build. Each step ends with a result you can check before you move on, and links back to the lesson it relies on.

The program is **jobrun**, the job runner you built in the [advanced project](../../advanced/project-async-plugin-tool/). It reads a JSON file of jobs, runs them concurrently under a deadline, and prints one line per job. You will release version 0.2.0.

## The specification

- The `primes` job is at least 20 times faster, with the same answers.
- `--log-level` and `--log-format text|json` turn on logs on standard error. Every log line names the job it came from, without passing the job around.
- On `SIGTERM`, jobrun cancels the unfinished jobs, still prints the report with those jobs as `cancelled`, and exits with code 143 (128 + 15, the signal number). Ctrl-C exits with 130.
- `--pool thread` runs CPU work in threads, which run in parallel on the free-threaded build. `--version` prints the version, which is written in one place only.
- `uv build` produces a wheel. The test suite passes with warnings as errors, on 3.15 and on 3.15t.

## Step 1: measure before you change anything

The obvious suspect is `count_primes`, the CPU job. Do not trust the suspicion; profile it. A sampling profiler sees only the process it samples, and jobrun computes in pool workers, so put the function alone in a script, with a large enough input to collect a thousand samples:

```python title="slow_primes.py"
"""count_primes as the advanced project left it, alone in one script."""
from math import isqrt


def count_primes(below: int) -> int:
    count = 0
    for n in range(2, below):
        for d in range(2, isqrt(n) + 1):
            if n % d == 0:
                break
        else:
            count += 1
    return count


print(count_primes(1_000_000))
```


## Step 2: one optimisation, checked

The sieve of Eratosthenes crosses out the multiples of each prime instead of testing each number. In Python it is fast when the crossing out is one slice assignment on a `bytearray`, so the inner loop runs in C. Keep the error for an impossible input, because a test depends on it:

```python title="src/jobrun/builtin.py (changed: count_primes)"
def count_primes(below: int) -> int:
    """The sieve of Eratosthenes. It still runs in a worker pool."""
    if below < 2:
        raise ValueError(f"below must be at least 2, got {below}")
    is_prime = bytearray([1]) * below
    is_prime[0] = is_prime[1] = 0
    for n in range(2, isqrt(below - 1) + 1):
        if is_prime[n]:
            # Cross out n*n, n*n + n, ... in one slice assignment.
            is_prime[n * n :: n] = bytes(len(range(n * n, below, n)))
    return is_prime.count(1)
```

`len(range(n * n, below, n))` is the number of positions the slice covers, computed without building a list. Now check both promises: the same answers, and a real speed-up, measured as in [measuring performance](../measuring-performance/) with the best of several runs:

```python title="check_sieve.py"
import timeit
from math import isqrt

from jobrun.builtin import count_primes


def trial_division(below: int) -> int:
    """The step 0 version, kept here as the reference answer."""
    count = 0
    for n in range(2, below):
        for d in range(2, isqrt(n) + 1):
            if n % d == 0:
                break
        else:
            count += 1
    return count


same = all(count_primes(b) == trial_division(b) for b in range(2, 3000))
print("same answers for 2..2999:", same)
print("primes below 1,000,000:", count_primes(1_000_000))

old = min(timeit.repeat(lambda: trial_division(100_000), number=1, repeat=5))
new = min(timeit.repeat(lambda: count_primes(100_000), number=1, repeat=5))
print("at least 20x faster:", old / new >= 20)
```

```text
same answers for 2..2999: True
primes below 1,000,000: 78498
at least 20x faster: True
```

**Check:** three lines as shown. The comparison covers every input from 2 to 2,999, including the edge cases 2 and 3, and the count below a million matches step 1. On the machine used for this lesson the measured ratio was about 290x to 400x, on both builds, so a 20x threshold leaves a wide margin for slower machines; if you get `False`, print `old / new` and run it three times. The suite still passes: 20 tests.

## Step 3: logs that name the job

When six jobs run at once, a log line is useless unless it says which job wrote it. Passing a job ID to every function would change every signature. A [context variable](../config-observability/#context-variables) does it without that, because every `asyncio` task runs in its own copy of the context. `logs.py` holds the variable, a filter that copies it onto each record, and two formats: plain text for people, and one JSON object per line for a log collector.

```python title="src/jobrun/logs.py"
import json
import logging
import sys
from contextvars import ContextVar

# Each asyncio task runs in its own copy of the context, so every job
# sees its own value here without passing it around.
job_id: ContextVar[str] = ContextVar("job_id", default="-")


class JobFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.job = job_id.get()
        return True
```

```python title="src/jobrun/logs.py (continued)"
class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        return json.dumps({"level": record.levelname,
                           "job": getattr(record, "job", "-"),
                           "message": record.getMessage()})


TEXT = logging.Formatter("%(levelname)s %(job)s: %(message)s")


def setup(level: str, form: str) -> None:
    """Send the jobrun loggers to stderr, as text lines or JSON lines."""
    handler = logging.StreamHandler(sys.stderr)
    handler.addFilter(JobFilter())
    if form == "json":
        handler.setFormatter(JsonFormatter())
    else:
        handler.setFormatter(TEXT)
    logger = logging.getLogger("jobrun")
    logger.handlers[:] = [handler]
    logger.setLevel(level)
    logger.propagate = False
```

`getattr` with a default keeps `mypy --strict` content, since `LogRecord` declares no `job` attribute. Logs go to standard error, so the report on standard output stays clean for pipes. In the runner, the old `execute` becomes `attempt`, unchanged, and a new `execute` sets the variable and logs around it. Setting it without a reset is safe here: the task's copy of the context disappears when the task ends.

```python title="src/jobrun/runner.py"
import asyncio
import logging
import signal
from collections.abc import Callable

from .config import Config
from .logs import job_id
from .models import Context, Outcome, Status
from .plugin import Plugin

log = logging.getLogger("jobrun.runner")


async def attempt[T](job: Plugin[T], ctx: Context, timeout: float) -> Outcome:
    try:
        async with asyncio.timeout(timeout):
            value = await job.run(ctx)
    except TimeoutError:
        detail = f"no result after {timeout}s"
        return Outcome(job.job_id, Status.TIMEOUT, detail)
    except Exception as error:
        detail = f"{type(error).__name__}: {error}"
        return Outcome(job.job_id, Status.FAILED, detail)
    return Outcome(job.job_id, Status.OK, job.render(value))


async def execute[T](job: Plugin[T], ctx: Context, timeout: float) -> Outcome:
    job_id.set(job.job_id)  # only this task's copy of the context changes
    log.info("started")
    outcome = await attempt(job, ctx, timeout)
    log.info("%s: %s", outcome.status, outcome.detail)
    return outcome
```

## Step 4: stop cleanly on SIGTERM

A scheduler or container runtime stops jobrun with `SIGTERM`. By default that kills the process at once: no report, and no record of which jobs finished ([stopping cleanly](../config-observability/#stopping-cleanly)). The report needs a status for jobs that never finished, so `Status` gains a member:

```python title="src/jobrun/models.py (changed: Status)"
class Status(StrEnum):
    OK = "ok"
    FAILED = "failed"
    TIMEOUT = "timeout"
    CANCELLED = "cancelled"
```

`run_all` installs a handler with `loop.add_signal_handler()` for as long as the jobs run. The handler cancels every task. A task cancelled from outside does not make the `TaskGroup` fail; the group simply waits for the rest, so the code after it still runs. On Windows, or outside the main thread, the loop cannot install the handler, and `on_sigterm` says so instead of failing.

```python title="src/jobrun/runner.py (continued)"
def on_sigterm(loop: asyncio.AbstractEventLoop,
               stop: Callable[[], None]) -> bool:
    """Call stop() on SIGTERM. False where the loop cannot do it (Windows)."""
    try:
        loop.add_signal_handler(signal.SIGTERM, stop)
    except (NotImplementedError, RuntimeError):
        return False
    return True


def outcome_of(task: asyncio.Task[Outcome]) -> Outcome:
    if task.cancelled():
        return Outcome(task.get_name(), Status.CANCELLED, "stopped by SIGTERM")
    return task.result()
```

```python title="src/jobrun/runner.py (continued)"
async def run_all(config: Config, ctx: Context) -> list[Outcome]:
    loop = asyncio.get_running_loop()
    tasks: list[asyncio.Task[Outcome]] = []

    def stop() -> None:
        log.warning("SIGTERM: cancelling the unfinished jobs")
        for task in tasks:
            task.cancel()

    watching = on_sigterm(loop, stop)
    try:
        async with asyncio.TaskGroup() as tg:
            for job in config.jobs:
                coro = execute(job, ctx, config.timeout)
                tasks.append(tg.create_task(coro, name=job.job_id))
    finally:
        if watching:
            loop.remove_signal_handler(signal.SIGTERM)
    return [outcome_of(task) for task in tasks]
```

Each task is named after its job, which is how `outcome_of` knows whose task was cancelled. To try it, run jobrun as a child process, wait until the quick job has finished, and send the signal. `stop.json` has a word count, a 0.05-second wait and a 30-second "nightly sync":

## Step 5: the command line

`cli.py` grows a thread pool, the logging options, `--version` and the exit codes from the specification. The [CLI lesson](../cli-apps/) covered `choices=` and exit codes. The version lives in `src/jobrun/__init__.py` as `__version__ = "0.2.0"`, and step 6 makes the build read it from there.

```python title="src/jobrun/cli.py"
import argparse
import asyncio
import signal
import sys
from collections import Counter
from concurrent.futures import (Executor, ProcessPoolExecutor,
                                ThreadPoolExecutor)
from pathlib import Path

from . import __version__, logs
from .config import load_config
from .models import ConfigError, Context, Outcome, Sink, Status
from .runner import run_all


def make_pool(kind: str, workers: int) -> Executor:
    match kind:
        case "process":
            return ProcessPoolExecutor(max_workers=workers)
        case "thread":
            return ThreadPoolExecutor(max_workers=workers)
        case "interpreter":
            from concurrent.futures import InterpreterPoolExecutor

            return InterpreterPoolExecutor(max_workers=workers)
        case _:
            raise ValueError(f"unknown pool kind {kind!r}")
```

`cancelled` is nine characters, so the status column is now ten wide, one more than before:

```python title="src/jobrun/cli.py (continued)"
def report(outcomes: list[Outcome], out: Sink) -> None:
    width = max((len(o.job_id) for o in outcomes), default=0) + 2
    for o in outcomes:
        out.write(f"{o.job_id:<{width}}{o.status:<10}{o.detail}\n")
    counts = Counter(o.status for o in outcomes)
    parts = [f"{counts[s]} {s}" for s in Status if counts[s]]
    out.write(f"{len(outcomes)} jobs: {', '.join(parts)}\n")


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="jobrun")
    parser.add_argument("jobs", type=Path, help="JSON file of jobs")
    parser.add_argument("--pool", default="process",
                        choices=["process", "thread", "interpreter"])
    parser.add_argument("--log-level", default="WARNING",
                        choices=["DEBUG", "INFO", "WARNING", "ERROR"])
    parser.add_argument("--log-format", default="text",
                        choices=["text", "json"])
    parser.add_argument("--version", action="version",
                        version=f"%(prog)s {__version__}")
    return parser
```

`asyncio.run` turns Ctrl-C into `KeyboardInterrupt` after cancelling its main task, so `main` catches it and returns 130 instead of printing a traceback:

```python title="src/jobrun/cli.py (continued)"
def main(argv: list[str] | None = None, out: Sink | None = None) -> int:
    args = build_parser().parse_args(argv)
    logs.setup(args.log_level, args.log_format)
    try:
        config = load_config(args.jobs)
    except (OSError, ConfigError) as error:
        print(f"jobrun: {error}", file=sys.stderr)
        return 2
    try:
        with make_pool(args.pool, config.workers) as pool:
            outcomes = asyncio.run(run_all(config, Context(pool)))
    except KeyboardInterrupt:
        return 130  # 128 + SIGINT, as shells report it
    report(outcomes, out if out is not None else sys.stdout)
    if any(o.status is Status.CANCELLED for o in outcomes):
        return 128 + signal.SIGTERM
    return 0 if all(o.status is Status.OK for o in outcomes) else 1
```

## Common pitfalls

- **Profiling the main process of a pooled program.** Tachyon would show the event loop waiting, because the work happens in worker processes. Profile the worker function alone, as step 1 did, or attach to a worker's process ID.
- **An optimisation without a reference.** Keep the old implementation in the check script until the new one has matched it on many inputs. The sieve's edge cases (2, 3, and squares of primes) are where a slice bound is off by one.
- **Calling `add_signal_handler` and never removing it.** The handler outlives `run_all` and cancels tasks that belong to some later call. The `finally` removes it.
- **A `SIGTERM` handler that does slow work.** The platform sends `SIGKILL` after its grace period. Cancel, report, exit; do not start new work.
- **A deadline or a cancel does not stop a process worker.** A cancelled `primes` job stops being awaited, but the worker keeps computing, and the pool's `with` block waits for it. Short CPU jobs keep shutdown short.
- **Two version numbers.** A version written in both `pyproject.toml` and `__init__.py` will drift. Write it once.

<Exercise title="Count the calls before you optimise">

Before changing `LogLevels`, find out how often it calls the regex engine. Run its `run` method once under `profiling.tracing` on a 1,000-line log, then use `pstats` to print the number of calls to `fullmatch` and to `splitlines`. Expected output:

```text
INFO=1000
    1 calls  <method 'splitlines' of 'str' objects>
 1000 calls  <method 'fullmatch' of 're.Pattern' objects>
```

<Solution>

```python title="count_calls.py"
import asyncio
import pstats
from concurrent.futures import ThreadPoolExecutor

import profiling.tracing

from jobrun.builtin import LogLevels
from jobrun.models import Context

LOG = "\n".join(f"09:00:{n % 60:02} INFO line {n}" for n in range(1000))
job = LogLevels("log", LOG)

profiler = profiling.tracing.Profile()
with ThreadPoolExecutor() as pool:
    value = profiler.runcall(asyncio.run, job.run(Context(pool)))
print(job.render(value))

functions = pstats.Stats(profiler).get_stats_profile().func_profiles
for name, profile in functions.items():
    if "fullmatch" in name or "splitlines" in name:
        print(f"{profile.ncalls:>5} calls  {name}")
```

```text
INFO=1000
    1 calls  <method 'splitlines' of 'str' objects>
 1000 calls  <method 'fullmatch' of 're.Pattern' objects>
```

A tracing profiler gives exact counts, which a sampling profiler cannot. One `fullmatch` per line is the minimum for this design, so there is no call to remove; if the plugin were slow, the next question would be the cost of each call. `get_stats_profile()` returns the table as objects, so you do not have to parse the printed report.

</Solution>
</Exercise>

<Exercise title="Does jobrun keep the GIL off?">

Write `gil_report.py`, which imports every jobrun module and then prints whether the interpreter is a free-threaded build, whether the GIL is enabled now, and the two flags that differ between the builds. Run it with `python3.15` and `python3.15t`. Expected on the default build:


<Solution>

```python title="gil_report.py"
import sys
import sysconfig

import jobrun.cli  # noqa: F401  Imports every jobrun module.

free_threaded_build = sysconfig.get_config_var("Py_GIL_DISABLED") == 1
print("free-threaded build:", free_threaded_build)
print("GIL enabled now:", sys._is_gil_enabled())
print("thread_inherit_context:", sys.flags.thread_inherit_context)

```

```console
context_aware_warnings: 1
```

`Py_GIL_DISABLED` describes the build, and `sys._is_gil_enabled()` describes the running process; they differ when an extension turns the GIL back on, which jobrun's imports do not. `thread_inherit_context` matters to jobrun's logging: on 3.15t, a thread started from inside a job would see that job's ID, while on the default build it would see `-`. ## Self-check

Answer each question in a sentence or two before you open the answers. If one stumps you, reread the linked lesson; these are the ideas the whole expert level rests on.

1. Why does a single timing of a function tell you so little, and what do you report instead?
2. A sampling profile shows a function with 900 cumulative samples and 10 direct ones. Where is the time?
3. When does `functools.cache` make a program slower or wrong?
4. What does the specialising adaptive interpreter do with a `BINARY_OP` that always sees two `int`s?
5. Why can an immortal object's reference count stop changing, and what problem does that solve for the free-threaded build?
6. An extension module does not declare `Py_mod_gil`. What happens when `python3.15t` imports it?
7. What is the difference between `Requires-Python` and a wheel's tag such as `cp315-cp315-manylinux_2_28_x86_64`?
8. Why should a library never call `logging.basicConfig()` or `sys.set_lazy_imports("all")`?
9. What happens to a Python service that receives `SIGTERM` and has no handler for it?
10. You upgrade to 3.15 and a test that used `assertWarns` starts failing with a warning it never showed before. Why?

<details>
<summary>Answers</summary>

1. Timings vary with the machine, other load and caches. Repeat, keep the minimum or a distribution, and compare with a margin wide enough to survive the noise ([measuring performance](../measuring-performance/)).
2. In the functions it calls: it is on the stack almost always, but rarely the one executing ([profiling](../profiling/)).
3. When arguments are unhashable or rarely repeat, when results are large and live forever, or when the function has side effects or depends on changing state ([optimising Python](../optimising-python/)).
4. It replaces the instruction in place with a specialised form for that case, and falls back if the types change ([the JIT and the interpreter](../jit-and-interpreter/), [bytecode](../bytecode-dis/)).
5. Its count is pinned at a special value and never decremented to zero, so it is never freed; threads then share it without writing to its count, which removes contention ([memory management](../memory-model/), [GIL internals](../gil-internals/)).
6. The GIL is turned back on for the whole process, with a `RuntimeWarning`, unless `PYTHON_GIL=0` or `-X gil=0` forces it off ([GIL internals](../gil-internals/)).
7. `Requires-Python` says which versions the project supports at all; the tag says which interpreter, ABI and platform one built file can run on ([packaging](../packaging-publishing/)).
8. Both change global behaviour for every program that imports the library. Those choices belong to the application ([configuration and observability](../config-observability/), [large codebases](../large-codebases/)).
9. It dies at once with the default action: no `finally` blocks, no `atexit`, no flushed logs ([configuration and observability](../config-observability/#stopping-cleanly)).
10. Since 3.15, `assertWarns` no longer swallows warnings that do not match the expected category, so a warning that was hidden now reaches the warning filters, which may turn it into an error ([upgrading to 3.15](../migrating-to-315/#porting-to-315-behaviour-that-changed)).

</details>

This is the end of the expert level and of the Python track.
