You already know the basic tools from [Measuring speed with timeit and cProfile](../../intermediate/profiling/): `python -m timeit`, `timeit.repeat`, taking the `min`, and checking that a fast version still gives the right answer. This module is about doing that work well enough to base decisions on it. This lesson covers measurement. [Profiling](../profiling/) finds where the time goes, and the later lessons cover what to do about it.

A benchmark answers one narrow question: *on this machine, with this interpreter and this input, which of these is faster, and by how much?* Most bad performance decisions come from benchmarks that answered a different question from the one asked.

## Pick the right clock

Python has several clocks, and they measure different things:

- `time.perf_counter()` is the highest-resolution clock available. It counts wall time, including sleeps and waits, and it is **monotonic**: it never jumps backwards. Use it for elapsed time. `perf_counter_ns()` gives integer nanoseconds.
- `time.process_time()` counts CPU time used by this process, in all its threads. Sleeping and waiting for I/O do not count.
- `time.time()` is the calendar clock. NTP or a user can adjust it, so it can jump. Never benchmark with it.

`time.get_clock_info` tells you each clock's properties:

```python title="which_clock.py"
import time

for name in ["perf_counter", "process_time", "time"]:
    info = time.get_clock_info(name)
    print(f"{name:12} monotonic={info.monotonic} adjustable={info.adjustable}")

wall_start, cpu_start = time.perf_counter(), time.process_time()
time.sleep(0.2)                       # waiting, not computing
wall = time.perf_counter() - wall_start
cpu = time.process_time() - cpu_start

print("wall clock saw the sleep:", wall >= 0.19)
print("CPU clock ignored it:", cpu < 0.05)
```

```text
perf_counter monotonic=True adjustable=False
process_time monotonic=True adjustable=False
time         monotonic=False adjustable=True
wall clock saw the sleep: True
CPU clock ignored it: True
```

When wall time and CPU time disagree a lot, the program is waiting. No amount of faster Python code will fix that. Look at I/O, locks, or the [concurrency models](../../advanced/concurrency-models/) instead.

## A harness you can trust

`timeit` already does the hard parts: it disables garbage collection during the run, uses `perf_counter`, and runs the statement in a loop so the clock's resolution does not matter. What it leaves to you is choosing the loop count and reporting more than one number. Here is a small harness that calibrates the loop count, repeats, and returns the best and the median:

```python title="bench_harness.py"
import statistics
import timeit


def bench(stmt, setup="pass", repeat=5, target=0.02):
    """Return (best, median) seconds per execution of stmt."""
    timer = timeit.Timer(stmt, setup)
    number = 1
    while timer.timeit(number) < target:   # calibrate the loop count
        number *= 2
    runs = [t / number for t in timer.repeat(repeat, number)]
    return min(runs), statistics.median(runs)


setup = "words = ['spam'] * 10_000"
join_best, join_median = bench("''.join(words)", setup)
loop_best, _ = bench("s = ''\nfor w in words: s = w + s", setup)

print("best <= median:", join_best <= join_median)
print("prepend loop slower than join:", loop_best > join_best)
print("at least 20x slower:", loop_best > 20 * join_best)
```

```text
best <= median: True
prepend loop slower than join: True
at least 20x slower: True
```

The **best** run is your estimate of the code's real cost, since noise only ever adds time. The **median** tells you how noisy the machine was. If the median is more than about 10% above the best, something else was competing for the CPU, so close it and measure again. `Timer.autorange()` does the same calibration as the loop above, aiming for 0.2 seconds per run. <Since v="3.15" /> You can change that target with `autorange(target_time=...)` or `python -m timeit --target-time`, and the command-line output is in colour by default (set `NO_COLOR=1` to turn it off).

Notice what the script prints: comparisons with a wide margin, not times. Raw times belong in your notes, along with the machine, the Python version and the input size. A claim like "at least 20x slower" survives a different laptop. "316 µs" does not.

For results you will publish or act on across releases, use [pyperf](https://pyperf.readthedocs.io/), the tool behind CPython's own benchmark suite. It runs each benchmark in several fresh processes, discards warm-up runs, and reports the mean and standard deviation. `python -m pyperf system tune` reduces CPU frequency scaling noise on Linux, and `pyperf compare_to old.json new.json` says whether a difference is significant.

## Growth rate versus constant factors

The [fundamentals lesson on Big O](../../../fundamentals/beginner/big-o/) describes how cost grows with input size. Measurement lets you check the growth rate directly: time the code at `n` and at `10 * n`, and look at the ratio. A linear algorithm takes about 10 times longer, a constant-time one about the same, and a quadratic one about 100 times longer.

```python title="growth_rate.py"
import timeit


def per_call(stmt, n, number):
    setup = f"data = list(range({n})); s = set(data); x = {n} - 1"
    return min(timeit.repeat(stmt, setup, number=number, repeat=5)) / number


for stmt, number in [("x in data", 200), ("x in s", 200_000)]:
    small = per_call(stmt, 10_000, number)  # cheap code needs more loops
    big = per_call(stmt, 100_000, number)
    growth = big / small               # 10x more data: how much slower?
    if growth > 5:
        shape = "grows with n (linear)"
    elif growth < 2.5:
        shape = "flat (constant)"
    else:
        shape = "unclear, measure again"
    print(f"{stmt:10} {shape}")
```

```text
x in data  grows with n (linear)
x in s     flat (constant)
```

Growth rate decides what happens as data gets bigger. Constant factors decide what happens at the size you actually have. At ten items a linear scan of a tuple can beat building a set, because building the set costs more than the few comparisons it saves. So measure at realistic sizes, and at a larger one too if your data will grow.

## When not to measure, and when not to optimise

Most code does not need a benchmark. If a function runs once at start-up, or takes a millisecond inside a request that waits 200 ms for a database, a 2x speed-up changes nothing a user can notice. Measure when you have a concrete target, such as a request deadline, a batch window or a frame budget, and a profile that points at the code. Without a target you cannot know when to stop, and without a profile you are probably measuring the wrong thing. Prefer the clearer version unless a measurement shows the other one matters at your real input size.

## Common pitfalls

**Timing set-up along with the work.** Put data creation in `setup`, or the benchmark measures `list(range(...))` instead of your code.

**Benchmarking something lazy.** A generator expression, `map` or `filter` object does no work until consumed. Timing its creation measures nothing (exercise 2).

**Comparing across machines or versions.** CPython gets faster every release, often by changing which idioms are fast. A result from 3.10 may be wrong on 3.15.

**Trusting one run.** Use the best of several runs, and look at the spread.

**Folklore.** "`+=` on strings is quadratic" is false for CPython in most loops, but true for other implementations. Measure on the interpreter you ship.

<Exercise title="Four ways to build a string">

Here are four ways to build a string from a list of words. For each, measure the time for 1,000 words and for 10,000 words (best of 5 runs) and classify the growth: call it `quadratic` if the larger input takes more than 40 times longer, otherwise `linear`. Check that all four give the same string. Use 10-character words such as `f"{i:09d} "`. Predict the result for `plus_equals` before you run it.

```python title="string_growth.py"
import io
import timeit


def plus_equals(words):
    s = ""
    for w in words:
        s += w
    return s


def prepend(words):
    s = ""
    for w in reversed(words):
        s = w + s
    return s
```

```python title="string_growth.py (continued)"
def join(words):
    return "".join(words)


def string_io(words):
    buf = io.StringIO()
    for w in words:
        buf.write(w)
    return buf.getvalue()
```

Expected output, one line per function: `plus_equals linear`, `prepend quadratic`, `join linear`, `string_io linear`.

<Solution>

```python title="string_growth.py (continued)"
def best(fn, words):
    return min(timeit.repeat(lambda: fn(words), number=1, repeat=5))


small = [f"{i:09d} " for i in range(1_000)]
big = [f"{i:09d} " for i in range(10_000)]
for fn in [plus_equals, prepend, join, string_io]:
    assert fn(big) == join(big)
    growth = best(fn, big) / best(fn, small)
    shape = "quadratic" if growth > 40 else "linear"
    print(f"{fn.__name__:12} {shape}")
```

```text
plus_equals  linear
prepend      quadratic
join         linear
string_io    linear
```

`prepend` copies the whole string on every step, so its total work grows with the square of the length. `plus_equals` looks as if it should too, but CPython resizes the string in place when nothing else refers to it. That optimisation is a CPython implementation detail, and PEP 8 advises against relying on it, so `"".join` remains the portable choice. `join` is also the fastest by a constant factor, because the loop runs in C.

</Solution>
</Exercise>

<Exercise title="The impossibly fast generator">

This benchmark says a generator expression is more than 50 times faster than a list comprehension doing the same work. Explain why the result is wrong, then fix the benchmark so both versions do the full computation. After the fix, the two should be within 3 times of each other: print `same ballpark (within 3x): True`.

```python title="lazy_bench.py"
import timeit

setup = "data = list(range(10_000))"
as_list = min(timeit.repeat("[x * x for x in data]", setup,
                            number=100, repeat=5))
as_gen = min(timeit.repeat("(x * x for x in data)", setup,
                           number=100, repeat=5))

print("generator is faster:", as_gen < as_list)
print("generator is 50x faster:", as_gen * 50 < as_list)
```

```text
generator is faster: True
generator is 50x faster: True
```

<Solution>

The generator expression is never iterated. Creating it costs the same for 10 items or 10 million, and none of the squares are computed. Consume both results the same way, here with `sum`:

```python title="lazy_bench_fixed.py"
import timeit

setup = "data = list(range(10_000))"
as_list = min(timeit.repeat("sum([x * x for x in data])", setup,
                            number=100, repeat=5))
as_gen = min(timeit.repeat("sum(x * x for x in data)", setup,
                           number=100, repeat=5))

ratio = as_gen / as_list
print("same ballpark (within 3x):", 1 / 3 < ratio < 3)
```

```text
same ballpark (within 3x): True
```

The list version is usually a little faster, and the generator uses far less memory. Which one matters depends on the size of the data ([Memory](../memory-profiling/)).

</Solution>
</Exercise>

<Exercise title="A verdict, not a number">

Write `compare(a, b, setup="pass", margin=1.25)` that times two statements (best of 5 runs of 500 executions each) and returns `"a"` or `"b"` when that one is faster by more than the margin, and `"tie"` otherwise. Test it on these three pairs, with `setup = "data = list(range(5_000)); s = set(data)"`:

- `"4_999 in data"` against `"4_999 in s"`
- `"sorted(data)"` against itself, with `margin=2`
- `"data[:]"` against `"[x for x in data]"`

Expected output: `b`, `tie`, `a`, one per line.

<Solution>

```python title="compare_tool.py"
import timeit


def compare(a, b, setup="pass", margin=1.25):
    """Say which statement is faster, or 'tie' within the margin."""
    ta = min(timeit.repeat(a, setup, number=500, repeat=5))
    tb = min(timeit.repeat(b, setup, number=500, repeat=5))
    if ta * margin < tb:
        return "a"
    if tb * margin < ta:
        return "b"
    return "tie"


setup = "data = list(range(5_000)); s = set(data)"
print(compare("4_999 in data", "4_999 in s", setup))
print(compare("sorted(data)", "sorted(data)", setup, margin=2))
print(compare("data[:]", "[x for x in data]", setup))
```

```text
b
tie
a
```

The margin is what makes the answer stable. Two runs of the same code never take exactly the same time, so without a margin the second line would say `a` or `b` at random. Even 25% can be too tight for identical code on a busy machine, which is why the tie test uses a margin of 2. Slicing copies the list in one C call, while the comprehension runs a bytecode loop.

</Solution>
</Exercise>

## Summary

- Use `perf_counter` for elapsed time and `process_time` for CPU time. Never benchmark with `time.time()`.
- Calibrate the loop count, repeat, and report the best run plus the spread. <Since v="3.15" /> `--target-time` and coloured output arrived in the `timeit` CLI.
- Report ratios and growth rates with a clear margin. Keep raw times in your notes, with the machine and version.
- Check that the code under test really does its work, and that it gives the right answer.
- Measure only when there is a target to meet. Next: [Profiling](../profiling/), to find where the time goes.
