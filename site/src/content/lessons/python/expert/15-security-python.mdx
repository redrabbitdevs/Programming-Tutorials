The [fundamentals lesson on security basics](../../../fundamentals/beginner/clean-code-and-security-basics/) set out the principles: never trust input, never build commands out of it, keep secrets out of code. This lesson is about where Python specifically makes those mistakes easy, and the standard-library tools that fix them. Every demonstration here is harmless: the "attacks" only print text.

## Randomness for secrets

`random` is a simulation tool. Its generator is designed to be reproducible, and its future output can be predicted from enough past output. Anything an attacker must not guess, such as a reset link, a session ID or an API key, comes from `secrets`, which reads the operating system's cryptographic source:

```python title="tokens.py"
import random
import secrets

# random is a simulation tool: the same seed gives the same "secret".
random.seed(2026)
first = random.getrandbits(64)
random.seed(2026)
print("random repeats itself:", first == random.getrandbits(64))

# secrets reads the operating system's cryptographic source.
token = secrets.token_urlsafe(32)
print("token_urlsafe(32):", len(token), "characters")
print("token_hex(16):", len(secrets.token_hex(16)), "characters")

# Compare secrets in constant time, never with ==.
sent = "Z3k9-reset-code"
print(secrets.compare_digest(sent, "Z3k9-reset-code"))
print(secrets.compare_digest(sent, "Z3k9-reset-codX"))
```

```text
random repeats itself: True
token_urlsafe(32): 43 characters
token_hex(16): 32 characters
True
False
```

32 random bytes is what the `secrets` documentation considers sufficient for typical use. `==` on strings stops at the first difference, so its timing leaks how much of a guess was right; `compare_digest` takes the same time either way.

## Passwords

Never store a password, and never store a plain fast hash such as `sha256(password)` either: an attacker with your database can try billions of guesses per second. Use a deliberately slow, salted key-derivation function. The standard library has `hashlib.scrypt`:

```python title="passwords.py"
import hashlib
import os
import secrets


def hash_password(password, salt=None):
    """Return (salt, digest). A new random salt unless one is given."""
    salt = salt or os.urandom(16)
    digest = hashlib.scrypt(password.encode(), salt=salt,
                            n=2**14, r=8, p=1)
    return salt, digest


def check_password(password, salt, digest):
    _, candidate = hash_password(password, salt)
    return secrets.compare_digest(candidate, digest)


salt, digest = hash_password("correct horse")
print(len(salt), len(digest))
print(check_password("correct horse", salt, digest))
print(check_password("correct hors", salt, digest))
print(hash_password("correct horse")[1] == digest)
```

```text
16 64
True
False
False
```

The last line shows why the salt matters: the same password hashed twice gives different digests, so one precomputed table cannot crack every account. Store the salt and the cost parameters next to the digest. In a web framework, use its password hasher, which does all this and can raise the cost over time.

## Running other programs

`subprocess` with a list of arguments never involves a shell: each list item reaches the program as exactly one argument, whatever characters it contains. `shell=True` hands one string to `/bin/sh`, which interprets `;`, `|`, `$( )` and the rest. This demonstration (for Linux and macOS) runs `echo` three ways with a hostile file name:

```python title="shell_injection.py"
import shlex
import subprocess

# Imagine this came from a web form. The payload only runs `echo`.
name = "report.txt; echo INJECTED: a second command ran"


def show(label, **kwargs):
    result = subprocess.run(capture_output=True, text=True, **kwargs)
    print(label)
    print("   ", result.stdout.rstrip().replace("\n", "\n    "))


show("list of arguments, no shell:", args=["echo", name])
show("shell=True and an f-string:", args=f"echo {name}", shell=True)
show("shell=True and shlex.quote:",
     args=f"echo {shlex.quote(name)}", shell=True)
```

```text
list of arguments, no shell:
    report.txt; echo INJECTED: a second command ran
shell=True and an f-string:
    report.txt
    INJECTED: a second command ran
shell=True and shlex.quote:
    report.txt; echo INJECTED: a second command ran
```

In the middle case the shell ran a second command chosen by the "user". Here it was `echo`; in an attack it is whatever the attacker likes. Use the list form. If you truly need a shell feature, quote every value with `shlex.quote`, which is correct for POSIX shells only. `os.system` and `os.popen` always use a shell, so avoid them for anything that includes input. A value starting with `-` can still be read as an option by the target program, so put `--` before user-supplied file names where the program supports it.

## Why pickle runs code

`pickle` does not store data; it stores instructions for rebuilding objects, and an object chooses those instructions through `__reduce__`. Any callable will do:

```python title="pickle_risk.py"
import pickle


class Surprise:
    def __reduce__(self):
        # "To rebuild me, call print with this argument."
        return (print, ("unpickling ran code chosen by the sender",))


data = pickle.dumps(Surprise())
print("the payload names a function:", b"print" in data)
print("loading it...")
result = pickle.loads(data)
print("loads returned", result)
```

```text
the payload names a function: True
loading it...
unpickling ran code chosen by the sender
loads returned None
```

The receiving program never mentions `Surprise`. The payload alone decided to call `print`, and an attacker would choose `os.system` instead. Hence the warning in the [pickle documentation](https://docs.python.org/3/library/pickle.html): never unpickle data that could have come from an untrusted source or been tampered with. For data that crosses a trust boundary, use JSON or another format that can only describe data. If you must read pickles, an allow-list `Unpickler` restricts which globals can be loaded:

```python title="pickle_allowlist.py"
import io
import pickle
from datetime import date


class AllowListUnpickler(pickle.Unpickler):
    ALLOWED = {("datetime", "date")}

    def find_class(self, module, name):
        if (module, name) in self.ALLOWED:
            return super().find_class(module, name)
        raise pickle.UnpicklingError(f"{module}.{name} is not allowed")


def safe_loads(data):
    return AllowListUnpickler(io.BytesIO(data)).load()
```

`find_class` is the one place where a pickle turns a name into a real object, so refusing there stops the payload before anything is called:

```python title="pickle_allowlist.py (continued)"
class Surprise:
    def __reduce__(self):
        return (print, ("this must not run",))


print(safe_loads(pickle.dumps({"due": date(2026, 10, 14)})))
try:
    safe_loads(pickle.dumps(Surprise()))
except pickle.UnpicklingError as error:
    print("refused:", error)
```

```text
{'due': datetime.date(2026, 10, 14)}
refused: builtins.print is not allowed
```

## Paths from users

A file name from a request can contain `..` or be absolute. The [pathlib lesson](../../intermediate/pathlib/) covered joining and resolving; here the point is refusing. Resolve the joined path and check that it is still inside the folder you meant:

```python title="safe_path.py"
import tempfile
from pathlib import Path


def safe_join(base, user_path):
    """Resolve user_path inside base, or refuse."""
    base = base.resolve()
    target = (base / user_path).resolve()
    if not target.is_relative_to(base):
        raise ValueError(f"{user_path!r} is outside the upload folder")
    return target


with tempfile.TemporaryDirectory() as root:
    uploads = Path(root, "uploads")
    uploads.mkdir()
    for request in ["report.txt", "2026/march.csv",
                    "../secrets.env", "/etc/passwd"]:
        try:
            target = safe_join(uploads, request)
            print("allowed:", target.relative_to(uploads.resolve()))
        except ValueError as error:
            print("refused:", error)
```

```text
allowed: report.txt
allowed: 2026/march.csv
refused: '../secrets.env' is outside the upload folder
refused: '/etc/passwd' is outside the upload folder
```

Joining an absolute path replaces the base entirely, which is why `/etc/passwd` needs the check as much as `..` does. `resolve()` also follows symbolic links, so a link inside the folder that points outside it is refused too.

## TLS, XML and archives

Three kinds of input arrive from outside without ever passing through your own parsing code: a server's certificate, an XML document and an archive.

**TLS.** `ssl.create_default_context()` loads the system's trusted certificates and checks both the certificate chain and the host name. The usual "fix" for a certificate error switches verification off, which lets anyone between you and the server read and change the traffic:

```python title="tls_defaults.py"
import ssl


def describe(label, context):
    print(f"{label:<10}", context.verify_mode.name,
          "check_hostname =", context.check_hostname)


describe("default", ssl.create_default_context())
describe("unverified", ssl._create_unverified_context())

# The usual "fix" for a certificate error, done in the wrong order:
context = ssl.create_default_context()
try:
    context.verify_mode = ssl.CERT_NONE
except ValueError as error:
    print("ValueError:", error)

# To trust a private CA, add it; do not switch verification off.
# context = ssl.create_default_context(cafile="company-ca.pem")
```

```text
default    CERT_REQUIRED check_hostname = True
unverified CERT_NONE check_hostname = False
ValueError: Cannot set verify_mode to CERT_NONE when check_hostname is enabled.
```

Never ship `_create_unverified_context`, `CERT_NONE` or a library's `verify=False`. For an internal certificate authority, pass its certificate as `cafile`. <Since v="3.13" /> The default context also sets `VERIFY_X509_STRICT`, so it rejects some malformed certificates that older versions accepted.

**XML.** Entity declarations let a short document expand enormously. This "billion laughs" document is 548 bytes:

```python title="xml_bomb.py"
import pyexpat
import xml.etree.ElementTree as ET

# Ten levels of entities, each one repeating the level below ten times:
# a few hundred bytes that would expand to a billion copies of "lol".
entities = ['<!ENTITY a0 "lol">']
for level in range(1, 10):
    entities.append(f'<!ENTITY a{level} "{f"&a{level - 1};" * 10}">')
BOMB = f"<!DOCTYPE bomb [{''.join(entities)}]><bomb>&a9;</bomb>"

print("input:", len(BOMB), "bytes")
print("Expat 2.7.2 or newer:", pyexpat.version_info >= (2, 7, 2))
try:
    ET.fromstring(BOMB)
except ET.ParseError as error:
    print("ParseError:", error)
```

```text
input: 548 bytes
Expat 2.7.2 or newer: True
ParseError: limit on input amplification factor (from DTD and entities) breached: line 1, column 537
```

The standard library's parsers use the Expat library, which refuses this, and does not fetch external files, as long as it is new enough. The [XML security](https://docs.python.org/3/library/xml.html#xml-security) section of the docs lists the attacks and says that Expat older than 2.7.2 may be vulnerable; check `pyexpat.EXPAT_VERSION`, because some Linux builds use the system's copy. For XML from strangers, the third-party `defusedxml` package wraps the same parsers and refuses entity declarations outright.

**Archives.** An archive member can be named `../outside.txt` or `/etc/cron.d/job`, or be a link to `/etc/passwd`. `tarfile`'s `data` filter rewrites or refuses each one:

```python title="tar_filter.py"
import io
import tarfile
import tempfile
from pathlib import Path


def hostile_archive():
    """An archive with one honest member and three escape attempts."""
    buffer = io.BytesIO()
    with tarfile.open(fileobj=buffer, mode="w") as tar:
        for name in ["notes.txt", "../outside.txt", "/etc/cron.d/job"]:
            info = tarfile.TarInfo(name)
            info.size = 2
            tar.addfile(info, io.BytesIO(b"hi"))
        link = tarfile.TarInfo("passwd")
        link.type, link.linkname = tarfile.SYMTYPE, "/etc/passwd"
        tar.addfile(link)
    buffer.seek(0)
    return buffer
```

```python title="tar_filter.py (continued)"
with tempfile.TemporaryDirectory() as folder:
    with tarfile.open(fileobj=hostile_archive()) as tar:
        for member in tar.getmembers():
            try:
                tar.extract(member, folder, filter="data")
                print("extracted:", member.name)
            except tarfile.FilterError as error:
                print("refused:  ", member.name, type(error).__name__)
    files = [p for p in Path(folder).rglob("*") if p.is_file()]
    print(sorted(p.relative_to(folder).as_posix() for p in files))
```

```text
extracted: notes.txt
refused:   ../outside.txt OutsideDestinationError
extracted: /etc/cron.d/job
refused:   passwd AbsoluteLinkError
['etc/cron.d/job', 'notes.txt']
```

The absolute name lost its leading slash and landed inside the folder. `data` is the default from 3.14; pass it explicitly to be safe on older versions. <Since v="3.15" /> [What's New 3.15](https://docs.python.org/3/whatsnew/3.15.html#tarfile) lists further fixes, each with a CVE: the filter now normalises link targets, extraction re-applies it when a link is replaced by a copy of another member (refusing with the new `LinkFallbackError`), and rejected members are no longer extracted when `errorlevel` is 0. Even so, the [tarfile documentation](https://docs.python.org/3/library/tarfile.html#hints-for-further-verification) says the filters are not enough for untrusted archives on their own: extract into a new empty folder and limit file count and total size. `zipfile` strips leading slashes and removes `..` components from member names when it extracts, but its documentation gives the same warning: inspect untrusted archives first.

## Other traps in the standard library

| Instead of | Use | Why |
|---|---|---|
| `eval(text)` to parse a literal | `ast.literal_eval(text)` or `json.loads` | `eval` runs any expression |
| `assert user.is_admin` | `if not ...: raise PermissionError` | `python -O` removes asserts |
| f-strings in SQL | driver placeholders, or [template strings](../../advanced/template-strings/) | SQL injection |
| `tarfile` `extractall()` on 3.13 and older | `extractall(path, filter="data")` | see [archives](#tls-xml-and-archives) above |
| a regex with nested quantifiers on user input | a simpler pattern and a length limit ([regex lesson](../../advanced/regex/)) | backtracking can take exponential time (ReDoS) |
| remote attaching left on in a process that must not be inspected | `-X disable-remote-debug` ([monitoring and debugging](../monitoring-debugging/)) | `pdb -p` and `sys.remote_exec` run code inside a live process |
| `tempfile.mktemp()` | `NamedTemporaryFile`, `mkstemp`, `TemporaryDirectory` | another process can take the name first |
| `yaml.load` with an unsafe loader (PyYAML) | `yaml.safe_load` | unsafe loaders can build arbitrary objects |

## Your dependencies

Most of the code you run, you did not write. Pin what you deploy with a lock file that records hashes, as in [building and publishing](../packaging-publishing/), so a replaced file is refused. Scan the pinned set for known vulnerabilities with an auditing tool such as the PyPA's `pip-audit`, in CI, on a schedule, not only when you change dependencies. Check a new dependency's name letter by letter before installing it, since typo-squatted names are a common attack, and prefer projects that publish with trusted publishing and attestations.

## When not to reach for more

Security effort should follow risk. A script that only you run on your own files does not need an allow-list unpickler, and `pickle` is fine for a cache your own program writes and reads. What is never fine is inventing primitives: do not write your own hashing scheme, encryption, escaping or sanitiser when `hashlib`, a vetted library or the list form of `subprocess` exists. And do not "sanitise" input for a shell when you can avoid the shell altogether.

## Common pitfalls

- **Checking a path with `str.startswith`.** `/srv/uploads-old` starts with `/srv/uploads`. See the last exercise.
- **Logging secrets.** The token you generated safely ends up in a log file. The [logging lesson](../../intermediate/logging/) shows a redacting filter.
- **Catching the injection only at the edge.** Data stored today is input to tomorrow's job. Treat values from your own database as untrusted when they reach a shell, SQL or HTML.

```python title="reset_secure.py"
import json
import secrets
import subprocess
import sys

MAILER = "import sys; print('mail to', sys.argv[1])"


def reset_token():
    return secrets.token_urlsafe(32)


def notify(email):
    command = [sys.executable, "-c", MAILER, email]
    result = subprocess.run(command, capture_output=True, text=True,
                            check=True)
    return result.stdout.strip()
```

## Summary

- Tokens come from `secrets`; compare them with `compare_digest`. Passwords get a salted, slow hash such as `hashlib.scrypt`.
- Pass `subprocess` a list. With an unavoidable shell, `shlex.quote` every value.
- Unpickling calls whatever the data names. Use JSON across trust boundaries, or an allow-list `Unpickler`.
- Resolve user paths and check them with `is_relative_to`. Prefer `literal_eval`, explicit checks over `assert`, and placeholders for SQL.
- Keep TLS verification on with `ssl.create_default_context()`. Parse untrusted XML with an Expat of 2.7.2 or newer, or `defusedxml`. Extract tar files with `filter="data"`, which 3.15 tightened again.
- Lock dependencies with hashes and audit them on a schedule.
